## 1. What changed since the plan: facts measured or verified

### 1.1 The query-embedding cost was mostly avoidable overhead (measured; `../../artifacts/m5_spikes.json`, `research/m5-spikes/`)
The plan sized the fleet on "1.23 s of a core to embed one question" (about 3.2 dedicated cores at the gate load with a cold cache). Profiling shows 98% of that time is the weight-matrix kernel `MatMulNBits` (1.177 s of 1.199 s) and that the cost has a floor of about 1 s even for a 4-token input. The model builder never sets the `accuracy_level` attribute, so ONNX Runtime dequantizes every weight to float32 on every call. Setting `accuracy_level=4` on the 196 nodes (same weights, no re-quantization, tested on a scratch copy; ORT 1.29.0, the production pin):

| One question (about 32 tokens) | shipped model | accuracy_level=4 |
|---|---|---|
| 1 thread | 1.22 s | **0.31 s** |
| 2 threads | 0.90 s | **0.18 s** |
| a 4-token input | 1.04 s | 0.046 s |
| a 257-token passage (upload embedding) | 2.74 s | 2.48 s (almost unchanged) |

Retrieval parity over the real corpus (60 benchmark/example questions against the 3,152 vectors the live site searches, with the production query prompt; `scripts/verify_embedder_parity.py`, result in `research/m5-spikes/parity_prod_prompt.json`): query-vector cosine to the current model mean 0.99876 (min 0.99793); the top-8 set is identical for 81.7% of questions (mean overlap 0.9729, minimum 0.75); the top-1 chunk is identical for **93.3%** (it changed for 4 of 60 questions); the top-10 mean overlap is 0.98 (minimum 0.9). **The pre-registered top-1 gate (>= 95%) FAILS** (section 1.4 item 12; the earlier figures here, 96% / 83% / 0.979 over 53 questions, were measured wrongly and are withdrawn). The four changed top-1 chunks sit on near-ties under the current model (score gap between its top-1 and the patched model's pick: 0.0001 to 0.0057 in cosine). Free evidence against the fp32 reference (`research/m5-spikes/fp32_reference.json`, same questions and corpus; not a redefinition of the gate): the shipped 8-bit model agrees with fp32 on top-1 for 98.3% of questions (1 disagreement), the patched model for 95.0% (3 disagreements); cosine to fp32 mean 0.99927 vs 0.99799; worst-case score regret 0.0017 vs 0.0065. So on top-1, cosine and worst-case regret the patched model is a slightly less faithful approximation of fp32, not only a different one; on mean top-8 overlap with fp32 it is marginally closer (0.9688 vs 0.9646), so the evidence is clearly unfavourable on the top-1 rank that gate (1) measures and mixed on ranking depth. The in-build gate (cosine to a level-0 twin over 53 questions) passed: mean 0.99877, min 0.99825 (`research/m5-spikes/patch_gate_report.json`). **Not measured yet:** the paid answer benchmark with the patched model, the same timings on Fly hardware, and CPU per ask outside embedding. A related ORT issue (#29849) reports a first-token change for level 4 in Qwen3-0.6B text generation; the parity above is our direct evidence for embeddings. Prefix-KV reuse was tried and is not possible with the current export.

Derived (assumes a Fly core 19% slower than the desktop, from the owner's G4 test; UNVERIFIED on Fly): at 2.6 live asks/s, embedding load is about **1.0 core-s/s with a cold cache and 0.33 warm**, versus 3.9 and 1.3 before. This removed the case for hosted query embedding.

### 1.4 Corrections to earlier statements (mine, the plan's, or a chairman's)
1. **"$35.09 (VERIFIED)" for today's API machine was an estimate, not an invoice.** Fly's formula gives $32.24 after 2026-10-01. Neither has been reconciled with a real invoice (the owner can read the Fly dashboard). Today's hosting is about $41.19/30 days derived ($32.24 + the Neo4j machine $8.50 + its 3 GB volume $0.45; bandwidth excluded), not $44-49.
2. **"Strict CSP" overstated today's page.** The live CSP allows `script-src 'self' 'unsafe-inline' https://challenges.cloudflare.com` and `style-src 'self' 'unsafe-inline'`. What actually protects the page: `connect-src 'self'`, no `unsafe-eval`, no HTML from the server (text only), restricted frames/forms/base, and the tests that pin those. A Next.js static export is therefore no worse on scripts; the header is set by FastAPI either way.
3. **My earlier M4 claim "no throttling on a fresh machine" was overstated.** The machine was restarted, not newly created, so its burst balance was probably full. `artifacts/m4_live_gates.json` is corrected (`risk13_restarted_machine_burn`). A fresh machine's throttling will be measured directly (section 3).
4. **The code comment on `ip_hash` says "non-reversible", which is not true for IPv4.** It is a 64-bit truncated unsalted SHA-256 of the address; the whole IPv4 space can be brute-forced. Not stated on any public page. Fix: HMAC with a secret pepper (decision 6) and nulling old values (decision 12).
5. **Council 1's chairman proposed `performance-1x 2 GB` as the first fallback if the live machine ever fails real demo traffic.** The M4 owner decision ("Bigger machine": 2 vCPUs and 4 GB, which the 30-page / 16,000-token caps and the 2.8 GB memory budget were set for) rules that machine out on memory and any 1-vCPU machine out on CPU (an upload would again compete with questions for the only core). Only **performance-2x 4 GB (+$51.53)** keeps the M4 decision; **performance-1x 4 GB (+$24.88)** keeps 4 GB but has one full vCPU, so it is also a departure from the M4 decision and would need the owner's sign-off.
6. **"Commit the parity test as CI on the built file" is not possible in GitHub Actions:** the model is built inside the Docker image from the 2.4 GB original weights. The gate lives in the image build stage (attribute present on all 196 nodes plus a cosine check against the unpatched build) and in a committed pre-merge script whose result is committed under `artifacts/`.
7. **Council 1's benchmark threshold ("no headline metric more than 2 points below baseline") is zero tolerance on 23 judged questions** (one question is 4.3 points). A flip caused only by judge noise would block shipping. The rule stays as the council set it (a miss is reported, never re-rolled, every flipped verdict is read and explained); if a noise-only flip happens, the evidence goes to the owner, who decides. I have not waived anything.
8. **The plan's $9-14 Valkey cost was UNVERIFIED; it is $8.65.** Moot, since Valkey is deferred.
9. **Staging limits.** Council 1 says staging keeps "the slots limiter and degrade path at production values" while Council 2 sets staging embedding slots at least 2 and in-flight above about 40. Reconciled here: the admission logic and degrade path run at production settings in the separate production-settings run; for the 1,000-user gate run the fleet-wide in-flight cap is **at least 120** (M5_PLAN.md section 6: twice the spike's about 60 streams, because shed requests count as errors with no carve-out) and embedding slots equal the cores available. "Above about 40" is a floor, not the value.

For buyer demos, a temporary scale-up with the rehearsed runbook (about $0.12/hour for a performance-2x 4 GB, derived, assuming per-second billing), decided per demo.

Never "the site supports 1,000 concurrent users"; the internal report lists every test exception and states that the live fleet differs. Owner approval needed for this sentence because it rewords a recorded owner decision.
- **Staging rules:** staging may stub Turnstile and raise caps only in staging config, a test proves live refuses both, and a separate run at production settings proves the sixth ask per IP is refused and the site degrades cleanly at the daily ceiling; every gate run starts on freshly booted machines and the first 10 minutes are reported separately (a restart empties the embedding cache), and the cache is never pre-warmed from the 300-question test pool (that would game the test); the load generator (k6 or Locust) runs on its own machine in `sin` through the public hostname (the staging apps are reachable from the internet only with a secret origin header and are destroyed after each window), and a generator above 70% CPU voids the run; the staging app refuses to boot against live's Neo4j host; `kill_signal` and `kill_timeout` are set explicitly, streams drain on shutdown, no deploy during a gate window or demo, and one rolling-deploy drill is reported separately.

### 2.2 State, admission and failure policy (Council 2; the five advisors were unanimous, the reviewers' objections were decided one by one)
- **Defer Valkey.** Live is one machine, where process-local state is correct, and Neo4j's capacity for the service state (about 10 reads/s and 7 writes/s at the gate load, derived; a Neo4j that is a 1 GB `shared-cpu-1x`) has never been measured. Valkey would add an unreplicated failure point (a deploy takes it down), a recurring cost and a new secret before any measurement shows a need. Upstash is rejected (not Valkey, a vendor with 2026 incidents). Neo4j-only is not rejected as "never": it is the baseline S7 measures.
- **Build now:** the async rewrite of the answer path and the embedder fix (both binding); a `StateBackend` protocol with an **in-process** backend for live (counters in memory, durable rows in Neo4j) and a **neo4j** backend (the rollback, and any multi-machine staging). **Deferred:** Valkey, the four Lua scripts, job-progress streams, the fleet in-flight cap, the sweeper lock.
- **Contract (tested on every backend):** `reserve` atomically checks the kill switch, the 150/day count, the $10 cap, the per-IP caps and the in-flight cap, increments, and writes a durable `reserved` ledger row before returning a lease; failure rolls back and denies. Tests: 200 concurrent reserves against 150 grant exactly 150; a double reconcile charges once; kill-then-boot leaves the counters equal to the ledger. **Boot rebuilds** the count, spend, per-IP daily counts and paid windows from the ledger (rows carry the hashed IP) and charges any pre-boot `reserved` row (a stream killed by a restart, a dead lease) its estimate. Windows and caches otherwise reset; killed upload jobs show "interrupted"; freshness shows "not checked since restart". On SIGTERM: refuse new paid asks and uploads, finish streams within `kill_timeout` 300 s.
- **When Neo4j is unreachable or a state operation takes over 1 s:** paid asks fail closed (503, the paused copy); cached answers are unavailable and never fall through to a paid call; the kill switch is cached (10 s refresh, an admin flip is immediate) and paid asks are off when it is stale over 30 s or at boot until read; failed reconciles are retried, else charged their estimate at boot; uploads refused; reads 503.
- **Policy:** both caps bind and whichever trips first pauses paid asks for the day (the $10 estimate-based cap, with an expired lease charged its estimate set as a per-ask-type upper bound, agent separate; plus the existing 150/day count). Three-level kill switch (on / retrieval_only / off). `IP_HASH_PEPPER`: HMAC-SHA256, a Fly secret, a version id stored on each row; rotate only on exposure (it resets windows and breaks correlation); IPv6 bucketed by /64; trust only `Fly-Client-IP` in production (verified in code: `guard.client_ip` and `CLIENT_IP_HEADER` in fly.toml). The Langfuse hash salt stays as is (one machine; a shared salt needs a rotation plan first). Embedding slots: 1 on live, equal to the cores available on staging (at least 2); in-flight LLM cap: 2 on live until S2 measures per-stream memory, at least 120 on the staging gate run (1.4 item 9).
- **Abuse:** before Turnstile only the answer-cache read remains (a 10 reads/s process budget); a **per-IP daily paid cap of 20** forces at least 8 Turnstile-passing addresses to drain the 150, so the worst case is a pause, never spend above $10 (decision 11). Staging has its own app, Neo4j and secrets; live refuses a stubbed Turnstile or raised caps.
- **Valkey triggers** (decided before the spikes run): **T1** S2 fails on one machine AND S7's state limits fail at 5 asks/s while retrieval passes (if S7 passes, a fleet uses the neo4j backend; if retrieval fails, price a bigger Neo4j machine first); **T2** the owner wants a multi-machine live fleet. If triggered: self-hosted Valkey 9.1.2 or later, `limits` with `valkey://`, a volume at `/data` with `--appendonly yes`, an explicit socket timeout, DNS retry, and the Lua and streams tested on it before use.

## 3. Pre-registered limits for the two spikes (fixed now, before they run)

**S7: Neo4j service state under sustained load.** A Neo4j-only replay harness in `sin` (no API, no LLM) against a staging clone of live's Neo4j (`shared-cpu-1x`, 1 GB). Levels 5, 10 and 20 live asks/s plus cached asks at the gate ratio (about 0.8 per live ask). Operation mix: the M5a mix (per live ask: 1 cache read, 1 reserve write, about 5 retrieval reads, 2 writes after) with today's mix as the control. Each level runs 60 minutes after a burst-draining soak (120 minutes if the drain is not visible in `cpu_balance`), judged on the last 30 minutes. **Pass:** pre-stream state-operation p95 <= 50 ms and p99 <= 200 ms; writes p95 <= 100 ms; retrieval p95 <= 1.5 x its own p95 at 0.5 live asks/s; errors <= 0.1%; zero lost ledger rows; no Neo4j restart or out-of-memory. M5a requires level 5 (about 1.9 x the gate's 2.6); levels 10 and 20 chart capacity.

**S2: one performance-class machine against the gate.** The size is fixed beforehand; cold start; generator in `sin`; the full load model; at least 60 minutes. **Pass:** the criteria of M5_PLAN.md section 6 (time-to-first-event p95 <= 1.5 s, at least 40 concurrent live streams held with 0 drops, errors < 0.5%, CPU <= 70% of the class's sustained CPU; the traffic model itself is PLAN.md:33), no thread-pool starvation at about 40 streams, zero lost ledger rows, and zero overshoot in a 10-minute sub-run with the cap set below demand. A failure stays a failure; a bigger size is a new run. **Fresh-machine throttle probe (added by the main session, not a council decision):** on a newly created `shared-cpu-2x` run a sustained full-core load and record when throughput drops, to replace the 5 s / 500 s documentation with an observation. This matters for the LIVE site, not only staging: `scripts/ops.ps1 stop` removes the API machine and `start` creates a new one, so a demo right after a start may run on a machine with only seconds of burst balance. If the probe shows throttling within seconds, the runbook gets a warm-up (start the machine well before a demo, or run demo windows on a performance-class machine) and the owner is told. The probe machine costs about $0.045/hour (derived) and is part of decision 3.
