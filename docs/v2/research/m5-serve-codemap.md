## 1. Process-local state — what breaks with 2+ API machines

Everything below lives on `app.state`, i.e. in the memory of **one** uvicorn process. `fly.toml` today runs exactly one machine (`min_machines_running = 1`, `auto_stop_machines = "off"`, fly.toml:38-40) and the Dockerfile starts uvicorn with **no `--workers` flag** (Dockerfile:30) — one process, one event loop, one anyio threadpool. M5's "async serving" + Valkey admission item exists specifically because every one of these breaks the moment a second machine (or worker process) is added.

| State | Where | Created | Breaks how, with 2+ machines |
|---|---|---|---|
| **Per-IP rate limiters** (paid/free/read) | `serve/guard.py:34-54` (`class RateLimiter`), instantiated `serve/main.py:232-235` | `dict[str, deque]` per key, sliding window, capped at `MAX_BUCKETS=20_000` (guard.py:24, 51-53), **no lock** | Each machine sees only the requests that land on it. A client's effective rate limit is multiplied by the number of machines that happen to serve it (round-robin/anycast). `guard.py:1-8`'s own docstring says the single machine is "deliberate" and the scope is "process-local ... is the correct scope for per-IP limits". This is the literal target of M5's "Valkey admission (atomic reserve/reconcile) and limits". |
| **Answer concurrency slot** | `app.state.answer_slots = threading.BoundedSemaphore(settings.max_concurrent_answers)` (main.py:236) | one per process | `max_concurrent_answers=2` (config.py:68) becomes `2 × N` machines globally, uncoordinated — no shared knowledge of how many LLM calls are in flight fleet-wide, so provider-side rate limits (ITPM/RPM) or cost ceilings cannot be enforced centrally. |
| **Workspace-create / upload-per-address limiters** | `workspace_create_limiter`, `upload_limiter` (main.py:239-240), same `RateLimiter` class | per process | Same multiplication as above, applied to `workspace_create_per_day=3` and `uploads_per_hour=10` (config.py:116-117). |
| **Upload slot ("one upload at a time")** | `app.state.upload_slots = threading.BoundedSemaphore(1)` (main.py:241) | one per process | Docstring intent (`config.py:100` comment, `fly.toml:47-48`): "2 shared vCPUs … so an upload embeds on one core while live questions use the other". With 2 machines this becomes 2 concurrent embeds fleet-wide, each still claiming "the other core is free for asks" locally — CPU contention the current sizing does not budget for, not just a naming nit. |
| **`JobRegistry` (upload SSE fan-out)** | `uploads/jobs.py:111-190` (`class JobRegistry`), created lazily as `app.state.upload_jobs` (jobs.py:210-216) | in-memory, **per machine** by the class's own docstring (jobs.py:112-118: "In-memory, per-MACHINE") | A job's live event log exists only on the machine whose worker thread ran it (`run_upload_job`, jobs.py:567-588, launches a plain `threading.Thread`). A `GET /api/workspace/{ws}/jobs/{job_id}` SSE request that a load balancer routes to a **different** machine gets `try_watch()==None` (job unknown here, jobs.py:151-163) → `workspace_routes.py:437-453` falls back to **one** replay of the last Neo4j-persisted snapshot (`repo.get_job`) and **ends the stream** — the client sees no further progress even though the job is still actively running on the owning machine. `MAX_LIVE_WATCHERS_PER_JOB=3` (jobs.py:41) is therefore also only a per-machine cap: it does nothing to bound total watchers across machines, and does nothing at all for a watcher that lands on a non-owning machine (no registry entry to count against). |
| **Upload sweeper start-pass optimization** | `uploads/jobs.py:604-647` (`class _Sweeper`), `SWEEPER_START_OLDER_THAN_S = 0` (jobs.py:615), used only on the sweeper's very first pass (jobs.py:665-666) | per-process | The class's own docstring (jobs.py:642-647) is an explicit, self-documented **CRITICAL blocker**: *"MULTI-MACHINE WARNING: this reasoning breaks the moment more than one API machine can run this sweeper at once (or a rolling deploy overlaps the old machine still finishing a job with the new machine's sweeper already starting) — `older_than_s=0` at start would then fail a job that IS still running, just on a machine this process's registry can never know about."* This must be replaced with a real cross-machine lease (the comment names `serve.monitor`'s `SvcLease` as the template) before M5 ships 2+ machines, or every rolling redeploy will spuriously fail in-flight uploads on the other machine. |
| **Freshness monitor's in-memory `_last`** | `serve/monitor.py:242-251` (`FreshnessMonitor.__init__`, `self._last`, `self._state_lock`) | per-process | **The check itself IS cross-machine-safe** (arbitrated by the Neo4j `SvcLease`, see §2) — but `GET /api/freshness` and the `/api/stats` freshness block read `status_payload()`/`summary()`, which are documented as **"in-memory only"** (monitor.py:384-386, 445-451) and read `self._last`. A machine loads `self._last` from Neo4j **once, at boot** (`_load_persisted`, monitor.py:276-277) and only updates it again when **that same machine** wins the lease and runs `_run_check` (monitor.py:347-366). A non-lease-holding machine's `_last` therefore goes stale forever after boot — different machines will report different `checked_at`/`status`/`pending_count` for the same underlying `SvcFreshness` row, and a client whose requests land on the non-holder sees a monitor that looks perpetually "stale" or frozen at boot time. |
| **Freshness admin "Check now" bypasses the cross-machine lease** | `serve/monitor.py:368-382` (`check_now`) | — | `check_now` acquires only the **local** `self._busy` lock and calls `self._run_check()` directly. Compare `_try_check` (monitor.py:329-345), used by the background loop, which calls `_acquire_lease` **before** `_run_check`. `check_now` never calls `_acquire_lease` at all. Today (1 machine) this is harmless because `_busy` already serializes admin vs. background on that one process. With 2+ machines, hitting `POST /api/admin/freshness/check` on machine B while machine A's background loop holds the `SvcLease` and is mid-check causes **two concurrent live checks** (duplicate outbound SEC/Federal-Register HTTP calls, and two racing, un-CAS'd writes to `SvcFreshness` — `PUT_FRESHNESS_QUERY` is a plain `SET`, last writer wins). No test in `tests/test_serve_monitor.py` or `tests/test_serve_monitor_routes.py` exercises this path against a held lease — it is an untested gap, not just an unfixed one. |
| **`/api/stats` ledger cache** | `app.state.stats_cache`, set in `serve/routes.py:151-160` (`_ledger_cached`), TTL `stats_cache_seconds=30` (config.py:72) | per-process | Low severity: each machine computes/caches its own ledger snapshot independently. Not a correctness bug (the underlying `SvcQuery` scan is still per-request-consistent), just duplicated Neo4j label-scan work and up to 30 s of display skew between machines. |
| **Dossier cache** | `app.state.dossier_cache`, `serve/dossier_routes.py:33-44` (`_cached`), 60 s TTL per `(endpoint, ticker[, limit])` | per-process | Same low-severity duplication as the stats cache; read-only derived data, no correctness impact. |
| **`RateLimiter` has no internal lock** | guard.py:39 (`defaultdict(deque)`, no `threading.Lock`) | — | Not exploitable **today**: every `.allow()` call is made synchronously from the single asyncio event-loop thread inside `async def` handlers (`routes.py:111`, `253`, `275`, etc.) — never from inside `_paid_stream`'s threadpool thread. It would become a genuine intra-process race only if a future change (e.g. calling `.allow()` from a worker thread, or running multiple asyncio loops in one process) introduced concurrent mutation; worth flagging as a fragile, undocumented invariant rather than a live bug. |

**Note on the freshness lease pattern itself** (worth reusing for M5's Valkey admission): `LEASE_QUERY` (monitor.py:58-63) and `store.reserve_daily_upload`'s `SvcUploadDay` counter (store.py:104-117) both use the same "SET before WHERE" trick — the unconditional `SET l._lock = true` (or `SET c._lock = true`) takes the node's write lock **before** the `WHERE` clause reads the guarded field, so two concurrent transactions racing for the same lease/slot cannot both observe the pre-update value (the lost-update pattern). This is the one properly atomic cross-process primitive already in the codebase and is a good reference for what the Valkey reserve/reconcile pattern needs to replicate.

## 2. Service state in Neo4j — labels and writes per request

Labels are prefixed `Svc` (service/operational) or `User` (M4 upload workspaces); `graph/schema.py`'s `PRIVATE_LABEL_PREFIXES` keeps them out of every public count (`serve/main.py:123-136`, `graph_stats`).

### `Svc*` labels (`serve/store.py:1-12`, `serve/monitor.py`)

| Label | Fields | Read on | Write on |
|---|---|---|---|
| `SvcPolicy {key, value, updated_at}` | `kill_switch` | every `/api/ask` (non-cache-hit path, `routes.py:268-269`) and every `POST /api/workspace/{ws}/documents` (`workspace_routes.py:372-373`), `GET /api/admin/policy` (`routes.py:425`) | `POST /api/admin/policy` (`routes.py:433`) |
| `SvcQuery {id, day, ip_hash, strategy, cached, prompt_tokens, completion_tokens, cost_usd, workspace, created_at}` | one row per answered question | daily-ceiling count `paid_queries_today` (`store.py:85-88`, on every `/api/ask` when `max_queries_per_day>0`, `routes.py:270`); `ledger_summary` label scan (today + all-time, `store.py:120-134`) on `/api/stats` (cached 30 s) and `GET /api/admin/policy` | `log_query` (`store.py:91-101`) — **once per** `/api/ask` attempt: on a `done`/`error` SSE event (`routes.py:369-371`), on a mid-stream `except` (`routes.py:397`), or, if neither fired, in the generator's `finally` for an abandoned/disconnected client (`routes.py:403-409`). ### `User*` labels (M4 upload workspaces, `uploads/repo.py`)

`UserWorkspace`, `UserDocument`, `UserVersion`, `UserUnit`, `UserChunk`, `UserPassage`, `UserJob` — every query is workspace-scoped (`{workspace_id: $ws, ...}`), one label per literal `MATCH` (repo.py:96-105 comment: a literal label lets the planner use `NodeByLabelScan`, never a bound `$labels` list, which forces a full `AllNodesScan`).

- `authenticate` (repo.py:168-182, `AUTH_LOOKUP_QUERY` repo.py:75-77) — read on every workspace route, before anything else (`serve/routes.py:220-230`, `_workspace_token_ok`).
- `touch` (repo.py:182-186, `TOUCH_QUERY` repo.py:78: `SET w.last_seen = $now`) — **write on every successfully authenticated workspace request** (`workspace_routes.py:110-117`, `_authenticate` calls it unconditionally after a successful token check), including read-only ones (GET workspace, GET job stream, GET changes, GET evidence).
- `create_workspace` (repo.py:156-167, `CREATE_WORKSPACE_QUERY` repo.py:72-74) — write on `POST /api/workspace`.
- `quota`, `get_workspace`, `latest_version`, `version_view`, `embedded_chunks`, `chunk_texts`, `search_chunks`, `get_changes`, `evidence` — reads, one or more Cypher round-trips per call, all on their own session (`graph/client.py:112-122`, one `driver.session()` per `run_cypher` call — **no batching, no shared transaction** across the several calls one HTTP request makes).
- `put_version` (repo.py:424-494) — the single write transaction per accepted upload version: creates/merges the `UserDocument`, creates the new `UserVersion`, supersedes the previous one if any, creates every `UserUnit` and `UserChunk` (with its embedding vector) and, for a re-upload, the diff `UserPassage` nodes — all inside one job's `indexing` stage (`uploads/jobs.py:505-517`).
- `put_job` (via `repo`, called from `uploads/jobs.py:232-264`, `_persist_job`) — one write per job-state transition (`received → validating → parsing → chunking → embedding → comparing → indexing → ready|failed`); a **terminal** write (ready/failed) is retried up to `PUT_JOB_RETRY_ATTEMPTS=6` times with doubling backoff (jobs.py:46-58), a non-terminal write is best-effort/single-attempt.
- `sweep_expired`, `sweep_orphans`, `fail_interrupted_jobs` — called once per sweeper cycle (`SWEEP_INTERVAL_S=15*60`, jobs.py:37) from **every** machine's own `_Sweeper` (idempotent, but redundant work and duplicate log lines with 2+ machines; the real correctness risk is the start-pass gap in §1).

## 3. `POST /api/ask` request path, end to end

1. **Handler is `async def ask(...)`** (`serve/routes.py:233-277`) — runs on the asyncio event loop.
2. Pure validation on the loop thread, no I/O: `guard.validate_question` / `validate_strategy` / `validate_as_of` (routes.py:237-239), `guard.client_ip` / `ip_hash` (routes.py:247-248).
3. **Gate order** (docstring, routes.py:1-7, matches the code exactly):
   `free_rate_limiter.allow` (process-local, sync, on-loop, routes.py:253-254) → workspace-token check **or** cache lookup (both `await run_in_threadpool(...)`, routes.py:255-266) → `kill_switch_on` (threadpool, routes.py:268-269) → `paid_queries_today` (threadpool, routes.py:270-271) → `verify_turnstile` (**true async**, `httpx.AsyncClient`, runs on the loop, 6 s client timeout, guard.py:130-155) → `rate_limiter.allow` (process-local, on-loop, routes.py:275-276).
   Every threadpool hop here checks a thread out of the **same shared anyio pool** (default ~40 workers; not pinned anywhere in this repo's own code, only asserted by the pre-M4 research doc) that also serves `/healthz`, `/api/stats`, `/api/evidence`, and every workspace route's `run_in_threadpool` calls.
4. On success: `return EventSourceResponse(_paid_stream(...), ping=15, sep="\n")` (routes.py:277).
5. **`_paid_stream` is a plain `def` — a synchronous generator** (routes.py:347, docstring: "Sync generator (runs in the threadpool)"). `sse_starlette`'s `EventSourceResponse`, given a sync iterator, drives it through Starlette's `iterate_in_threadpool` helper — the **exact mechanism** the `workspace_routes.py:391-405` comment block diagnoses as the CVE-2023-30798-shaped hazard it fixed for the upload job-watcher route ("`anyio.to_thread.run_sync` is not cancellable: each stuck watcher permanently pinned ONE thread ... a client disconnect could never free it"). **`/api/ask` was never rewritten this way and still has that shape**: one anyio threadpool worker is checked out and held for the **entire lifetime of the stream** — Neo4j retrieval, the LLM's token-by-token network read, and the closing Neo4j writes all run synchronously on that one thread. This is the literal "thread-per-stream sync generator" the plan itself names as a v1 blocker (`docs/v2/PLAN.md:33`, `docs/v2/M3_AGENT_PLAN.md:9`).
6. Inside `_paid_stream` (routes.py:347-411): acquire `st.answer_slots` non-blocking (routes.py:358, else yield a `busy` error and return) → retrieval + LLM via `_stream_fn(...)` (routes.py:365-367; for the SEC path this is `answer_stream` / `stream_answer_for_context`, `retrieval/answerer.py:593-644`, which runs `hybrid_retrieve` — **6–7 sequential, synchronous Cypher queries**, each its own `driver.session()` (`retrieval/retriever.py:676-763`, `graph/client.py:112-122`) — then hands the rendered prompt to `TextStream` (`answerer.py:349-426`), whose `litellm.completion(..., stream=True)` is itself a **synchronous** generator that blocks on the provider's HTTP/SSE response) → on `done`/`error`, `store.log_query` and (non-workspace, checks-clean) `store.put_answer` (routes.py:369-380, more blocking Neo4j writes on the same thread) → `finally`: log an abandoned query if nothing else did, close the per-request tracer, release `answer_slots` (routes.py:402-411).
7. **Where the event loop itself can block**: nowhere inside `_paid_stream` (it genuinely runs off-loop). The real contention is threadpool-token starvation: enough concurrent `/api/ask` streams (each holding a thread for the LLM's full 15–80 s duration) can exhaust the shared pool and delay **every other** `run_in_threadpool` call in the process — `/healthz`, `/api/stats`, workspace auth, evidence lookups — exactly the failure mode already observed and fixed once for the job-watcher SSE route (`workspace_routes.py:396-397`: "Enough stuck watchers starve every OTHER `run_in_threadpool` call in the whole process ... a full outage from a single job's worth of extra GETs"). `/api/ask` is the one SSE surface in this codebase that still has that shape.
8. **`sse_starlette` usage differs by route**: `/api/ask` uses `EventSourceResponse(gen, ping=15, sep="\n")` (routes.py:277) — a 15 s keep-alive comment so a quiet "thinking" stream survives proxy idle timeouts. The M4 job-stream route uses `ping=SSE_POLL_TIMEOUT_S` (10 s, `workspace_routes.py:59, 452`) because it is an **async** generator (`_job_event_stream`, workspace_routes.py:412-434) polling an in-memory log every `SSE_POLL_INTERVAL_S=0.5` s — it never touches the threadpool at all, and cancels immediately on client disconnect (`await asyncio.sleep` is a genuine cancellation point; `GeneratorExit` propagates cleanly). This async-generator pattern is the template `/api/ask` itself would need to follow for M5's "async serving" line item. Once Cloudflare fronts the service, note research-scale-frontend.md's verified fact that Cloudflare's proxy read timeout is 125 s — the current 15 s ping comfortably beats it.
9. `_sse()` helper (routes.py:115-116): `ServerSentEvent(data=json.dumps(event, default=str), event=event["event"], sep="\n")` — every event is a named SSE event (`retrieval`/`delta`/`escalated`/`done`/`error`/`job`), not the unnamed default, which is what the M5 AI-SDK encoder will need to map onto `data-*`/`text-*` parts.

## 4. Client-IP handling today, and what changes behind Cloudflare

- `guard.client_ip(request, trusted_header)` (`serve/guard.py:57-66`): if `trusted_header` (i.e. `settings.client_ip_header`) is configured **and present** on the request, take the first comma-separated value and strip it; otherwise fall back to `request.client.host` (the raw TCP peer).
- Production sets `CLIENT_IP_HEADER = "fly-client-ip"` (`fly.toml:26`) — trusted specifically because it is **Fly's own edge proxy** setting it from the real connection (guard.py:1-8 docstring: "Honoured ONLY when the deployment names it ... any other header is attacker controlled and would turn the per-address limiter into a no-op"). This is pinned by `tests/test_serve_api.py::test_spoofed_forwarding_header_is_ignored_unless_configured` and `::test_configured_header_keys_the_limiter`.
- `ip_hash()` (guard.py:69-71): `sha256(ip)[:16]` — the only form of the address that is ever persisted (`SvcQuery.ip_hash`) or logged; the raw IP never leaves `client_ip()`'s caller scope.
- **What M5's `CF-Connecting-IP` + origin-auth line means concretely**: this is a **one-line config change** (`CLIENT_IP_HEADER=CF-Connecting-IP`, `config.py:70`) — but it is only *safe* once Fly's origin is no longer reachable un-proxied ("origin-auth"). `CF-Connecting-IP` is a header **Cloudflare's edge adds**; if the Fly app can still be reached directly (bypassing Cloudflare), any client can set that header itself and defeat every per-IP gate at once — the same class of spoofing `guard.py`'s docstring already warns about for an untrusted header, just with a different name. **Nothing in the current code enforces or checks for origin-auth** (no shared-secret header check, no mTLS, no Fly private-networking-only binding for the public listener) — the M5 rollout must land the origin lock (e.g. a Cloudflare-only shared-secret header checked before `client_ip()` trusts `CF-Connecting-IP`, or Fly's own "Private Networking only + Cloudflare as the sole public entry" pattern) in the **same** change that flips `CLIENT_IP_HEADER`, not before it and not after.
- Multi-machine implication (ties back to §1): even with the header renamed correctly, every per-IP `RateLimiter` instance is still process-local. Cloudflare's anycast/round-robin routing means the same client IP can land on different API machines across requests within one rate-limit window, silently multiplying every per-IP limit (ask rate, free-tier rate, read rate, workspace-create/day, uploads/hour) by the number of machines that serve that client — this is the direct, concrete reason M5 replaces the in-process `RateLimiter` with Valkey-backed atomic admission rather than just relabelling the trusted header.
