## 2. Shared vs performance CPU semantics (VERIFIED, https://docs.fly.io/machines/cpu-performance)

Table, verbatim:

| CPU Type | Period | Baseline Quota | Initial Burst Balance | Max Burst Balance |
|---|---|---|---|---|
| `shared` | 80ms | 5ms (6.25%) | 5s | 500s |
| `performance` | 80ms | 80ms (100%) | - | - |

Quotes:
- "We enforce limits through the Linux scheduler's CPU bandwidth control by adjusting the `cpu.cfs_quota_us` setting on each machine cgroup. For each 80ms period of time, we set a quota of 5ms for each `shared` vCPU, or the full 80ms period for each `performance` vCPU. If your machine cgroup's CPU usage reaches its quota, its tasks will be 'throttled' (not scheduled to run again) for the remainder of the 80ms period."
- "Quotas are shared between a Machine's vCPUs. For example, a `shared-cpu-2x` Machine is allowed to run for 10ms per 80ms period, regardless of which vCPU is using that time."
- "we allow a balance of unused CPU time to be accrued. The application is then allowed to spend its balance in bursts. When bursting, the vCPU is allowed to run at up to 100%. When the balance is depleted, the vCPU is limited to running at its baseline quota."
- "a `shared` CPU with a burst balance of 500 seconds can burst for `500/(1-.0625)` = 533 seconds."
- Footnote: "We might change these specific numbers over time."
- Zero balance behaviour (docs, monitoring example): "When the balance reached 0, the Machine was briefly `throttle`d." There is a `fly_instance_cpu_throttle` metric.

Summary for sizing:
- shared-cpu-1x: baseline 6.25% of one core (5 ms per 80 ms). shared-cpu-2x: 10 ms per 80 ms in total = 12.5% of one core total (6.25% per vCPU, pooled). shared-cpu-4x would be 25% of one core.
- Burst balance: starts at 5 s, caps at 500 s (533 s of real 100% run time). Refill: the docs do not publish a numeric refill rate; only that unused CPU time accrues. INFERENCE: while fully idle the balance accrues at the unused part of the quota, i.e. about 0.0625 CPU-s per wall-s per vCPU, so refilling 0 -> 500 s takes about 8,000 s (2.2 h) on shared-cpu-1x and about 4,000 s on 2x. Treat as an estimate.
- At zero balance: hard cap at the baseline; within each 80 ms period, once the quota is used (5 ms per vCPU), tasks are descheduled for the rest of that period (stalls up to 75 ms on 1x). This is the latency risk for an API plus a Valkey on one shared-cpu machine.
- Performance vCPUs: quota is the full 80 ms of every 80 ms period (100% of a vCPU), no burst accounting. The docs say shared and performance "both run on the same physical hardware, have the same clock speed, etc... The difference is how much time they are allowed to spend running your applications." Fly does not use the word "dedicated" on this page and does not promise a pinned physical core. UNVERIFIED that performance vCPUs are exclusive hardware threads; VERIFIED that they are not quota-throttled.

## 4. kill_timeout, deploys and restarts

- VERIFIED max **300 seconds (5 minutes)**, default **5 seconds**; "best-effort". Source: https://docs.fly.io/reference/configuration#kill_timeout-option : "This sets how long Fly.io waits (in seconds) after sending the `kill_signal` before moving on to a forced shutdown ... The default is 5 seconds. You can set it up to a maximum of 300 seconds (5 minutes)." Warning in docs: "`kill_timeout` settings should be considered best-effort, and your app needs to be prepared to handle shorter stopping times". Top-level key in fly.toml, e.g. `kill_timeout = 120` (the long-running-tasks guide also shows `"30s"`).
- Applies to "`fly deploy`", "`fly machine stop`", and "when a machine stops due to `auto_stop_machines`" (same page). The blueprint adds host migrations.
- **Docs conflict on the default signal and the final step (read both, set explicitly):**
  - https://docs.fly.io/reference/configuration : default `kill_signal` is `SIGINT`; sequence listed as "1. Fly sends the kill_signal ... 2. It waits for up to kill_timeout seconds. 3. Then it sends SIGTERM unconditionally." (the "SIGTERM" in step 3 looks like a doc error given the intro says "forced shutdown").
  - https://docs.fly.io/blueprints/long-running-tasks : "Fly sends `kill_signal` (default: `SIGTERM`) to PID 1. After waiting `kill_timeout` seconds, it sends `SIGKILL`." Table: kill_timeout default 5s, max 300s.
  - Machines API / flyctl: https://docs.fly.io/machines/api/machines-resource : stop "Signal ... (default: SIGINT)", "Seconds to wait before sending SIGKILL to the Machine". `fly machine stop` and `fly machine restart`: `--signal` default SIGINT, `--time`/`--timeout` = seconds to wait before killing, `--force`, `--skip-health-checks` (https://docs.fly.io/flyctl/cmd/fly_machine_restart).
  - Recommendation: put `kill_signal = "SIGTERM"` and `kill_timeout = <N>` in fly.toml. PID 1 must receive the signal; a `sh -c` wrapper swallows it, use exec form.
- Rolling deploys: VERIFIED (https://docs.fly.io/blueprints/seamless-deployments) rolling is the default ("Replace Machines one at a time. Use `max_unavailable`"); "The platform won't kill a healthy Machine until a new one is up and running" given health checks and at least two Machines; canary and bluegreen "can't be used with attached volumes"; immediate updates all at once. A single Machine with a volume therefore cannot do bluegreen/canary, and Fly states there is downtime on each deploy.
- In-flight connections: Fly's docs frame kill_timeout as "a drain window": stop accepting new work, let in-flight work finish or checkpoint, exit cleanly (long-running-tasks). Fly-proxy stops sending traffic to a Machine that fails health checks. Nothing I found states that established TCP connections are handed off, so assume they are cut when the process exits or at SIGKILL. UNVERIFIED how fly-proxy treats already-open TCP flows to a stopping Machine (this applies to Flycast; direct 6PN traffic bypasses the proxy).
- `fly machine restart`: sends the signal then force-kills after `--time` seconds; whether it defaults to the Machine's configured kill_timeout when `--time` is omitted is UNVERIFIED.

## 6. Internal DNS, 6PN, Flycast for a private Valkey app

Primary: https://docs.fly.io/networking/private-networking and https://docs.fly.io/networking/flycast

What the API app needs to reach a self-run Valkey app (same org, default 6PN) - all VERIFIED:
1. Same organization (and the same private network; the default network unless you create custom ones). "Applications from other organizations can't" talk over 6PN.
2. DNS: `<valkey-app>.internal` returns an AAAA record containing "all the 6PN addresses of the started Fly Machines" of that app. Qualifiers: `<region>.<app>.internal` (e.g. `sin.valkey.internal`), `top1.nearest.of.<app>.internal`, `<machine_id>.vm.<app>.internal` (stable per-Machine name). "most [libraries] will only use the first address that is returned, but others might round-robin."
3. Valkey must listen on the 6PN address: "Your app's service needs to bind to/listen on `fly-local-6pn`" (alias in /etc/hosts for the Machine's 6PN IPv6 address; you may bind the address directly). Valkey/Redis ship with `bind 127.0.0.1 -::1` and `protected-mode yes` by default (UNVERIFIED here, general knowledge; not checked against Valkey's config today), which would not accept 6PN connections; set `bind fly-local-6pn` (or `::`) and a password/ACL. Fly's old Redis guide ("this document is old") confirms default private-only port 6379 with `REDIS_PASSWORD` and a volume at `/data` (https://docs.fly.io/app-guides/redis).
4. The client must speak IPv6 (AAAA only; no A record). 6PN addresses "are not static and will change over time", so re-resolve DNS on reconnect rather than caching an IP; use `<machine_id>.vm.<app>.internal` for a stable per-Machine name.
5. No `[services]`/`[http_service]` block and no public IP are needed for direct 6PN access: "6PN addresses directly connect one Fly Machine with another, bypassing the Fly Proxy." With no public IP allocated and no services, nothing is exposed publicly.
6. `.internal` AAAA answers include only **started** Machines: "Any stopped Machines, including those autostopped by Fly Proxy, are not included". So a stopped Valkey is simply unresolvable.
- Operational note (VERIFIED): Fly's infra log for 2026-09-15 describes a stuck-DNS bug in corro-dns (internal resolver) that left stale `_instances.internal` answers and says "We're also planning a bigger overhaul of our internal DNS setup" (https://fly.io/infra-log). Build clients with DNS retry/backoff.

Does Flycast matter for a single-instance Valkey? Flycast ("app.flycast", a private IPv6 routed by Fly Proxy) provides autostop/autostart, geographic load balancing, TLS/PROXY-protocol handling. Requirements (VERIFIED): a Flycast address (`fly ips allocate-v6 --private`), bind to `0.0.0.0:port` (binding to `fly-local-6pn` "won't work for Flycast"), and a `[[services]]` section. With one instance there is nothing to load balance; Flycast would add a proxy hop and make autostop possible (bad for an in-memory store). Fly says to use Flycast if you want Fly Proxy features and `.internal` otherwise. INFERENCE: use plain `.internal` for a single Valkey; consider Flycast only if you need autostart or a fixed address. UNVERIFIED: whether fly-proxy imposes an idle timeout on raw TCP flows that would cut long `XREAD BLOCK 0`/pub-sub connections (docs expose `idle_timeout` only under http_options); direct 6PN avoids the question.
