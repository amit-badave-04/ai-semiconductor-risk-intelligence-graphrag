## A. Cloudflare hosting

### A1. Pages vs Workers Static Assets
- VERIFIED: Cloudflare's Pages docs home carries the banner "Are you sure you want to use Pages? ... Workers supports most Pages use cases and offers a broader feature set. It is Cloudflare's primary platform for building applications. Start new projects with Workers." (https://developers.cloudflare.com/pages/index.md, page updated Aug 25 2026)
- VERIFIED: Workers best-practices page: "Workers Static Assets is the recommended way to deploy static sites, single-page applications, and full-stack apps on Cloudflare. If you are starting a new project, use Workers instead of Pages. Pages continues to work, but new features and optimizations are focused on Workers." (https://developers.cloudflare.com/workers/best-practices/workers-best-practices/index.md)
- VERIFIED: Pages is NOT formally labelled deprecated in the official docs I fetched; the migration guide (https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/index.md, updated Sep 22 2026) contains no "deprecated"/"maintenance" wording. UNVERIFIED (third-party only, via search snippets): the phrase "maintenance mode" is used by blogs, not by Cloudflare docs.
- Recommended deploy path for a new static site (VERIFIED, https://developers.cloudflare.com/workers/static-assets/get-started/index.md): `npm create cloudflare@latest -- my-static-site` (template "Static site"), `npx wrangler dev`, `npx wrangler deploy`. Best-practices page: "For a purely static site, point `assets.directory` at your build output. No Worker script is needed. For a full-stack app, add a `main` entry point and an `ASSETS` binding".
- Deploy target: "Your project can be deployed to a `*.workers.dev` subdomain or a Custom Domain" (same get-started page).

### A2. Free-tier limits (Workers Free)
Source: https://developers.cloudflare.com/workers/platform/limits/index.md (updated Sep 5 2026) and https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/index.md (updated Apr 23 2026).
- VERIFIED: Requests to static assets are "free and unlimited"; Worker script invocations are billed per Workers pricing. No extra cost for storing assets.
- VERIFIED: Files per Worker version: 20,000 (Free), 100,000 (Paid). Individual file size: 25 MiB (both). `_headers` rules 100; `_redirects` 2,000 static + 100 dynamic.
- VERIFIED: Bandwidth: no bandwidth figure or cap appears on the limits page or the static-assets billing page. UNVERIFIED that no cap exists (absence of evidence only).
- VERIFIED: Worker invocations on Free: 100,000/day (reset 00:00 UTC; over the limit -> Error 1027). CPU time 10 ms per HTTP request. 50 subrequests per invocation. 128 MB memory. 6 simultaneous connections waiting for response headers. Worker size 64 MiB.
- VERIFIED gotcha (billing page): if you use `run_worker_first`, matching requests always invoke the Worker; once the free daily request limit is exceeded "these requests will receive a 429 (Too Many Requests) response instead of falling back to static asset serving". Negative patterns (`!/...`) keep serving assets. `run_worker_first` can be an array of patterns (max 100 entries), e.g. `["/api/*", "!/api/docs/*"]` (https://developers.cloudflare.com/workers/static-assets/binding/index.md). So: static site free forever; every `/api/*` call through the Worker counts against the 100k/day.

### A3. workers.dev needs no domain
- VERIFIED: "Your `workers.dev` subdomain allows you getting started quickly by deploying Workers without first onboarding your custom domain to Cloudflare." URL form `<WORKER_NAME>.<YOUR_ACCOUNT_SUBDOMAIN>.workers.dev`. ### A4. Worker as reverse proxy to `something.fly.dev` (secret header, SSE)
- VERIFIED: Worker subrequests to arbitrary origins via `fetch()` are the standard pattern (docs example "Respond with another site": `return fetch("https://example.com")`, https://developers.cloudflare.com/workers/examples/respond-with-another-site/index.md). Secrets: `npx wrangler secret put NAME`, never in config (best-practices page).
- VERIFIED (streaming): "If your Worker only forwards subrequest responses to the client verbatim without reading their body text, then its body handling is already optimal"; "By default, Cloudflare Workers is capable of streaming responses ... To maintain the streaming behavior, you should only modify the response body using the methods in the Streams APIs." (https://developers.cloudflare.com/workers/runtime-apis/streams/index.md). Practical implication (inference): `fetch(new Request(originUrl, request))` with an added request header, returning the origin `Response` untouched, streams SSE without buffering in the Worker. I did not run it.
- VERIFIED (limits relevant to a streaming proxy): CPU time excludes network wait ("Waiting on network requests (such as `fetch()` calls ...) does not count toward CPU time"); HTTP-triggered Worker duration "No limit" while the client stays connected; "There is no set time limit on individual subrequests"; `waitUntil()` extends up to 30 s. Free CPU limit is 10 ms per request; average Worker uses ~2.2 ms (limits page). No official CPU figure for "bytes pumped through an unmodified stream" was found: UNVERIFIED that a long SSE pass-through stays under 10 ms CPU (likely, because pass-through is native, but not documented as a number).
- VERIFIED: runtime grace: runtime updates give in-flight requests a 30-second grace period before termination, "very unlikely" for long requests to hit it (limits page). Inference: clients should auto-reconnect SSE (EventSource does).
- VERIFIED (compressed SSE pitfall): workerd PR #7390 "Flush compressed server-sent events after writes" (opened 2026-09-16, still OPEN/unmerged today) states compressed `text/event-stream` can stay buffered inside gzip/Brotli encoders until more output arrives; identity-encoded SSE is unaffected. (https://github.com/cloudflare/workerd/pull/7390). Mitigation (inference): make the Fly origin send SSE uncompressed (no gzip/brotli, `Cache-Control: no-cache, no-transform`).
- UNVERIFIED (search snippet only; Cloudflare community page returned 403): community reports of Cloudflare proxy buffering `text/event-stream` and a staff statement that a fix was rolled out (https://community.cloudflare.com/t/sse-endpoint-breaks-after-recent-update-cloudflare-buffers-text-event-stream-desp/810790).

### A5. Idle timeouts / SSE guidance
Source: https://developers.cloudflare.com/fundamentals/reference/connection-limits/index.md (updated Jul 23 2026) and Error 524 page (https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/index.md).
- VERIFIED: Client <-> Cloudflare: HTTP/1.1 keep-alive 400 s; HTTP/2 idle 400 s (TCP closed; not configurable).
- VERIFIED: Cloudflare <-> origin: Proxy Idle Timeout 900 s (520); Proxy Read Timeout 125 s (524; Enterprise-configurable up to 6,000 s); Proxy Write Timeout 30 s; TCP ACK timeout 90 s; complete TCP connection 19 s.
- NOTE: many third-party pages say "100 seconds" for 524. The official page today says 125 s. Use the official figure.
- UNVERIFIED: whether the 125 s/900 s zone-proxy timeouts apply to a Worker's own `fetch()` subrequest to a non-Cloudflare origin (Workers docs only say subrequests have no set time limit). No official SSE guidance page was found. Safe practice (inference): origin sends a `: keepalive` SSE comment every ~15-30 s so no hop ever sees silence anywhere near any of these limits.

- VERIFIED (primary pricing table, https://www.cloudflare.com/zero-trust/products/access/): Free Plan "$0 forever", "Best for teams under 50 users or enterprise proof-of-concept tests"; Pay-as-you-go "$7 per user/month (paid annually)"; the "Core capabilities > Usage" row reads "50 user limit | No user limit | No user limit" (Free | PAYG | Contract). Free standard log retention "up to 24 hours". Feature list includes "Token authentication: Service token support for automated services", multiple IdPs, application launcher, mTLS.
- VERIFIED: onboarding needs payment details even on Free: "If you chose the Zero Trust Free plan, this step is still needed but you will not be charged." (https://developers.cloudflare.com/cloudflare-one/setup/index.md)
- VERIFIED: Identity providers: a new Zero Trust org gets the "Cloudflare identity provider" as default login; "You can add a one-time PIN or connect a third-party identity provider at any time." One-time PIN: "OTP is no longer added automatically, but you can set it up at any time" (https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/index.md, updated Aug 31 2026). Limits: 50 IdPs, 50 service tokens, 500 applications per account (https://developers.cloudflare.com/cloudflare-one/account-limits/index.md). I found no plan restriction on OTP; UNVERIFIED that OTP works on Free specifically (docs show no plan gating).
- VERIFIED: Access CAN protect `*.workers.dev`. "A specific hostname - can be `workers.dev`, a Custom Domain, or a path" via a self-hosted application; or "Protect one Worker" which "automatically protects every domain associated with the Worker, including its routes, Custom Domains, `workers.dev` hostname, and previews." No custom domain/zone needed. (https://developers.cloudflare.com/workers/configuration/cloudflare-access/index.md, updated Aug 18 2026; also workers-dev page).
- VERIFIED caveats from that page: worker-level Access policies do not support WebSocket upgrades (403; use hostname-based app); Workers with Static Assets run behind an internal router Worker so `ctx.access` is NOT passed to the user Worker. Use the `Cf-Access-Jwt-Assertion` header and validate it against `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs` (https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/index.md). SSE behind Access: not addressed in the docs (UNVERIFIED).
- Browser app on host A calling protected API on host B (VERIFIED, https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/cors/index.md, updated Aug 25 2026):
  - A CORS request must carry a valid `CF-Authorization` cookie for host B. Cookies are per-application-host.
  - Simple requests without a prior login to B fail with a CORS error. Preflight OPTIONS gets 403 because browsers never send cookies on OPTIONS; fix = enable "Bypass options requests to origin" or configure Access to answer preflights (Advanced settings > CORS settings).
  - The doc's cookie-free answer: a Worker that injects a service token (`CF-Access-Client-Id`/`CF-Access-Client-Secret`), "only works if both sites involved in the CORS exchange are behind Access". A service token must never be embedded in browser JS.
  - Multi-domain applications: one Access application can cover several hostnames and "preemptively set the cookie for every domain through a series of redirects" so SPAs can call other subdomains (https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/index.md); wildcard hostnames cannot get preemptive cookies. Cookie SameSite is configurable (None/Lax/Strict).
  - Incognito/third-party-cookie caveat in the CORS doc: `CF-Authorization` is blocked as a third-party cookie on cross-origin requests in private mode.
  - Public Suffix List check (VERIFIED, https://publicsuffix.org/list/public_suffix_list.dat): `workers.dev`, `pages.dev` and `fly.dev` are all on the PSL, so `app.x.workers.dev` -> `api.fly.dev` (or two workers.dev names) is cross-SITE; cookies between them are third-party cookies. Inference/recommendation: avoid cross-host auth entirely; serve the SPA and `/api/*` from the SAME workers.dev hostname (Worker with `run_worker_first: ["/api/*"]` proxying to Fly with a secret header), protect that one hostname with Access, and validate the JWT header in the Worker or at Fly.

## C. Hosted embedding for `Qwen/Qwen3-Embedding-0.6B`

Reference facts (VERIFIED, https://huggingface.co/Qwen/Qwen3-Embedding-0.6B/raw/main/README.md and config.json): Apache-2.0; embedding dimension "Up to 1024, supports user-defined output dimensions ranging from 32 to 1024"; context 32k; hidden_size 1024; `torch_dtype: bfloat16`. Query format: `f'Instruct: {task_description}\nQuery:{query}'` (no space after "Query:" in the Python snippets) while the card's TEI curl example uses `"...\nQuery: What is..."` (WITH a space). Documents get no instruction. Card says omitting the instruct on the query side costs about 1-5% retrieval quality. Paper (https://arxiv.org/html/2506.05176): causal attention, `[EOS]` appended, embedding = last-layer hidden state at EOS; query input `{Instruction} {Query}<|endoftext|>`.

### C0. Parity checklist (applies to EVERY hosted query embedder)
The hosted query vector must land in the same space as the stored document vectors (built locally with ONNX q8). Before switching, a live cosine check of hosted-vs-local query vectors on a sample of real queries is REQUIRED (plus recall@k on the eval set). Things that must match:
- Exact template string, including the `Query:{q}` (HF Python snippet) vs `Query: {q}` (HF TEI example) space discrepancy found in the card, and the exact instruction sentence.
- Normalization: DeepInfra's native route defaults `normalize` to False; the OpenAI-compatible route does not state a default (UNVERIFIED); Fireworks states Qwen3 output is unnormalized; Workers AI does not state it (UNVERIFIED). L2-normalize client-side if you compare by dot product.
- Dimension: 1024 native (HF card); do not pass `dimensions` unless the index was built with MRL truncation.
- Precision: hosted is bf16 or unstated vs local int8 dynamic/q8; small cosine drift is expected, so measure it.

### C1. DeepInfra - serves it: VERIFIED (that it is a "US host" is asserted by the requester and was not checked by me: UNVERIFIED)
- Model API metadata (https://api.deepinfra.com/models/Qwen/Qwen3-Embedding-0.6B): type embeddings, tags `openai`, `priority`; `max_tokens` 32768; price `cents_per_input_token: 1e-06` = $0.01 per 1M input tokens; `quantization: null` (precision not stated); not deprecated. Same JSON endpoint for the siblings: Qwen3-Embedding-4B `2e-06` = $0.02/M and Qwen3-Embedding-8B `1e-06` = $0.01/M (VERIFIED via api.deepinfra.com/models/Qwen/Qwen3-Embedding-4B and -8B; 8B being cheaper than 4B is what the API returns). The model page/listing also say "$0.010 / 1M tokens" for 0.6B (https://deepinfra.com/Qwen/Qwen3-Embedding-0.6B, https://deepinfra.com/models/embeddings).
- API shape (VERIFIED, https://docs.deepinfra.com/apis/embeddings.md and OpenAPI https://docs.deepinfra.com/api-reference/embeddings/openai-embeddings.md): OpenAI-compatible `POST https://api.deepinfra.com/v1/openai/embeddings`. Request fields: `model`, `input` (string or array, `maxLength: 1024` items), `encoding_format` (float|base64), `dimensions` (min 32; "If provided bigger than model's default, the embedding will be padded with zeros"), `input_type` (query|passage|document; described as controlling the query:/passage: prefix "on VL embedding models; ignored by symmetric models"), `service_tier` (priority|flex), `fail_fast`. There is NO `custom_instruction` field on the OpenAI-compatible route.
- Native route (VERIFIED from model metadata `txt_docs`): `POST https://api.deepinfra.com/v1/inference/Qwen/Qwen3-Embedding-0.6B` takes `inputs`, `normalize` (default False), `dimensions` (32-8192), and `custom_instruction` ("Custom instruction prepending to each input. If empty, no instruction will be used.", max 512 chars, example "Given a web search query, retrieve relevant passages that answer the query"). So the docs show no auto-prefix for this model on the OpenAI route (the only prefix-related field, `input_type: query`, is documented for VL models; whether it prefixes Qwen3 text models is UNVERIFIED), and the native route opts in via `custom_instruction`. Treat the safe assumption as "send the full Instruct string yourself and leave `input_type` unset" until a live comparison proves otherwise. UNVERIFIED: the exact template DeepInfra builds from `custom_instruction` (not tested; needs a key).
- Dimension: UNVERIFIED on DeepInfra directly; default is the model's native 1024 (HF card). The DeepInfra model page's description text is a copy of the 4B card ("Up to 2560"), so do not trust that page text for dims.
- Latency: UNVERIFIED (no primary source gives typical latency; would need a live call).
- Data policy (VERIFIED, https://docs.deepinfra.com/account/data-privacy and https://deepinfra.com/privacy): "Input data is not stored to disk during inference"; "We do not log the content of your requests. We log only metadata ... request ID, cost, sampling parameters"; "We do not use data you submit to our APIs for training models, except when using Google or Anthropic models" (not relevant to Qwen). Bulk inference APIs may retain data briefly in encrypted form.

## D. Valkey, Python clients, `limits`

### D1. Valkey versions and Docker image
- VERIFIED current stable: Valkey 9.1.2, release notes dated "Mon 31 August 2026" (https://raw.githubusercontent.com/valkey-io/valkey/9.1.2/00-RELEASENOTES), GitHub release published 2026-09-01T00:01Z (https://api.github.com/repos/valkey-io/valkey/releases). 9.1.2 is a SECURITY-urgency release (incl. an unauthenticated use-after-free of the Lua interpreter state). 9.1.0 GA was 2026-05-19. Maintenance lines: 9.0.6 (2026-09-01), 8.1.10 and 8.0.11 (2026-08-31), 7.2.14 (2026-07-21). 9.2.0-rc1 (2026-09-16) is a pre-release. Any pin should be >= 9.1.2 / 9.0.6 / 8.1.10 / 8.0.11. License BSD-3-Clause.
- VERIFIED Docker Hub tags (https://hub.docker.com/v2/repositories/valkey/valkey/tags): `latest`, `9`, `9.1`, `9.1.2` (+ `-alpine`, `-trixie`), `9.0.6`, `8.1.10`, `8.0.11`, `9.2.0-rc1`. (`library/valkey` Docker Official Image API returned 404; `valkey/valkey` is the Valkey project's own publisher repo, ~317M pulls.)
- Persistence defaults, VERIFIED from source/conf at tag 9.1.2:
  - RDB snapshotting is ON by default with no config: valkey.conf comment "Unless specified otherwise, by default the server will save the DB: after 3600 s if >=1 change, 300 s if >=100 changes, 60 s if >=10000 changes".
  - AOF is OFF by default: `appendonly no` (valkey.conf) and `createBoolConfig("appendonly", ..., server.aof_enabled, 0, ...)` (src/config.c).
  - VERIFIED the image entrypoint does not change persistence: `docker-entrypoint.sh` (https://raw.githubusercontent.com/valkey-io/valkey-container/mainline/9.1/debian/docker-entrypoint.sh, identical in alpine) only prepends `valkey-server` when the first arg is an option/`.conf`, chowns/drops privileges, sets umask 0077, and ends with `exec "$@" $VALKEY_EXTRA_FLAGS`. It injects no `--save`, `--appendonly` or config, so the server defaults above apply unless you pass flags. It warns that persistence errors occur if the working dir is not writable.
  - Image: `WORKDIR /data`, `CMD ["valkey-server"]`, no `VOLUME` instruction (valkey-container Dockerfile); Docker Hub README: "If persistence is enabled, data is stored in the `/data` directory" and shows `valkey-server --save 60 1` / `VALKEY_EXTRA_FLAGS='--save 60 1 --loglevel warning'`. To survive restarts on Fly, mount a volume at `/data`; to get AOF set `--appendonly yes` (not default). Without a mounted volume the RDB file is lost with the machine.

### D4. `limits` (PyPI) and redis-py 5/6/7/8
- VERIFIED: latest `limits` 5.8.0 (2026-02-05), MIT. Its `redis` extra requires `redis!=4.5.2,!=4.5.3,<8.0.0,>3` (PyPI metadata). So redis-py 5.x, 6.x and 7.x (up to 7.4.1) satisfy it; redis-py 8.x does NOT (pip resolves to 7.x or errors if you also pin 8). The `rediscluster` extra has no upper bound (`>=4.2.0`). `async-redis` extra is `coredis<6,>=3.4.0` (async default is coredis; redis-py async is opt-in via `limits.aio.storage.RedisStorage.implementation = "redispy"`).
- VERIFIED: the upper bound lags redis-py majors. Open issue #367 "Raise the `redis` extra upper bound to allow redis-py 8.x" (2026-08-02) and open PR #370 "Relax redis requirement to < 9.0.0" (2026-09-29, bumps lock to redis 8.1.0, adds redis 8.0 server to CI) are NOT merged/released as of today (https://github.com/alisaifee/limits/issues/367, /pull/370). The issue author notes the runtime only checks a minimum version (`DEPENDENCIES = {"redis": Version("3.0")}`) and that `register_script`/`evalsha`, INCR, EXPIRE, GET, TTL are not in redis-py 8's unified-response migration list, but says he did not run the suite on redis-py 8 (UNVERIFIED that it works).
- Valkey in `limits`: VERIFIED supported since 4.3 via `valkey://` scheme using the `valkey` package (extra `valkey`/`async-valkey` = `valkey>=6`); docs list Valkey servers 7.2 and 8.0 as CI-tested (https://limits.readthedocs.io/en/stable/storage.html).
- Options (inference): (1) stay on redis-py 7.4.1 and `limits[redis]`; (2) use `valkey-py` with `valkey://` storage (officially supported path); (3) use redis-py 8 with a pip override/`--no-deps` for limits and run limits' tests yourself, setting `socket_timeout` appropriately.

## E. ONNX Runtime MatMulNBits `accuracy_level`

### E1. Documented values
- VERIFIED (https://raw.githubusercontent.com/microsoft/onnxruntime/main/docs/ContribOperators.md, `com.microsoft.MatMulNBits`): "accuracy_level: The minimum accuracy level of input A, can be: 0(unset), 1(fp32), 2(fp16), 3(bf16), or 4(int8) (default unset). It is used to control how input A is quantized or downcast internally while doing computation, for example: 0 means input A will not be quantized or downcast while doing computation. 4 means input A can be quantized with the same block_size to int8 internally from type T1." `bits` supported values 2, 4, 8; `block_size` power of two, >= 16.
- VERIFIED (CPU kernel source, https://raw.githubusercontent.com/microsoft/onnxruntime/main/onnxruntime/contrib_ops/cpu/quantization/matmul_nbits.cc): enum comments `Level0 input fp32, acc fp32; Level1 input fp32, acc fp32; Level2 input fp16, acc fp16; Level3 input bf16, acc fp32; Level4 input int8, accumulator int32`. `GetComputeType`: if `accuracy_level == 4` AND `MlasIsQNBitGemmAvailable(nbits, block_size, SQNBIT_CompInt8)` -> `SQNBIT_CompInt8`; otherwise `SQNBIT_CompFp32` (for fp16 inputs on ARM64: `HQNBIT_CompInt8` at level 4 else `HQNBIT_CompFp16`). So on x64 CPU, levels 0-3 all mean fp32 compute and only 4 switches to int8 compute.

### E2. What level 4 does for 8-bit weights on CPU
- VERIFIED (MLAS source, https://raw.githubusercontent.com/microsoft/onnxruntime/main/onnxruntime/core/mlas/lib/qnbitgemm.cpp): for 8-bit weights MLAS has only `SQ8BitGemmVariant_CompInt8` (plus an ARM64 fp16 variant `HQ8BitGemmVariant_CompFp16`); there is NO 8-bit fp32-compute variant. `MlasIsQNBitGemmAvailable(8, ..., CompFp32)` returns false (default branch). In the operator, when MLAS has no kernel it logs "Falling back to using unpacked compute mode ... the weights will be de-quantized to fp32 before invoking the fp32 Matmul kernel" and runs `ComputeBUnpacked`. Net: for 8-bit weights, `accuracy_level=4` gives the packed int8 path (activations A dynamically quantized per `block_size` block to int8, int32 accumulation); any other value gives dequantize-then-SGEMM.
- VERIFIED: the new session option `mlas.qnbit.force_fp32=1` (PR #31723 merged 2026-09-19) only applies to float-input, `nbits_ == 4`, `block_size_ == 32`, level-4 nodes on x86/x64 (condition in the constructor). It does NOT help 8-bit nodes.
- VERIFIED activation quantization granularity (comment by a contributor on issue #29849, who read `QuantizeARow_CompInt8` in sqnbitgemm_kernel_avx2.cpp): per-block scale = maxabs(block)/127 along K with block = `BlkLen`, i.e. activation granularity equals weight block granularity. This is a third-party reading of source, consistent with the doc sentence "quantized with the same block_size to int8".

### E3. First release with 8-bit on CPU
- VERIFIED by tag diff: `onnxruntime/core/mlas/lib/qnbitgemm.cpp` at tag v1.21.1 has 0 occurrences of `SQ8BitGemmVariant_CompInt8` and at v1.22.0 has 7 (the `MlasIsQNBitGemmAvailable` switch contains the 8-bit case at v1.22.0); `matmul_nbits.cc` at v1.22.0 has `ORT_ENFORCE(nbits_ == 4 || nbits_ == 8, ...)`, whereas v1.21.1 has no 8-bit check. So the first ORT release with the x64 CPU 8-bit (int8-compute) MatMulNBits path is **v1.22.0** (2025-05-10). Consistent with PR #24491 "[x86] matmulnbit x64 kernel for 8bits" (merged 2025-04-24, https://github.com/microsoft/onnxruntime/pull/24491) and the v1.22.0 notes ("CPU EP/MLAS ... MatMulNBits Support ... weights quantized to 8 bits", https://github.com/microsoft/onnxruntime/releases/tag/v1.22.0).
- VERIFIED by tag diff: ARM64 8-bit: `qnbitgemm_kernel_neon.cpp` has 0 `SQ8Bit` references at v1.22.0 and 5 at v1.23.0, so ARM64 8-bit first ships in **v1.23.0** (2025-09-26); PR #25110 merged 2025-09-04. fp16 8-bit on ARM64: PR #27692 merged 2026-03-18 (release notes list it under v1.25.0). Current ORT on PyPI: 1.30.0 (2026-09-10) (also 1.29.1 and 1.28.3 patch lines exist on GitHub).
- VERIFIED perf from PR #24491 (AVX512-VNNI, 8-bit vs 4-bit): M=1 decode shapes 1.2x-6x slower than 4-bit; M=4096 about parity (0.93x-1.05x); on non-VNNI/AVX512 8-bit is 1.4-1.5x slower than 4-bit "because i16 cannot fit in 4 i8 ... extra instructions needed".

### E3b. Applicability: does this even apply to your current q8 embedder?
- `accuracy_level` exists only on `com.microsoft.MatMulNBits` nodes (and QMoE). The typical Transformers.js/onnx-community "q8"/"int8"/"uint8" files are NOT MatMulNBits. VERIFIED (https://raw.githubusercontent.com/huggingface/transformers.js/3.5.0/scripts/quantize.py, tag 3.5.0 / 3.7.0; the script no longer exists on `main`): `quantize_q8` uses ORT's `ONNXQuantizer` with `mode=QuantizationMode.IntegerOps`, `static=False` (dynamic), `activation_qType=QuantType.QUInt8` ("dynamic activation only supports uint8"), weights QInt8/QUInt8, i.e. dynamic quantization (MatMulInteger-style integer ops), and has no `accuracy_level` at all. Its `q4`/`q4f16` modes use `MatMul4BitsQuantizer` (MatMulNBits) with an `accuracy_level` option; `bnb4` uses MatMulBnb4. So `accuracy_level` is relevant only if the graph contains MatMulNBits (q4, an ORT `MatMulNBitsQuantizer` run with `bits=8`, or an ORT-GenAI builder export).
- UNVERIFIED (ONNX operator spec, not fetched today): `DynamicQuantizeLinear` quantizes activations per tensor (one scale/zero-point per tensor), unlike MatMulNBits level 4's per-block activation scale. Whether the dynamic-q8 graph is more or less accurate on massive-activation channels was not measured by anyone I found.
- Action for the caller: inspect the graph's op types (e.g. count `MatMulNBits` vs `MatMulInteger`/`DynamicQuantizeLinear`/`QLinear*`) of the model actually deployed before applying any of section E to it. I did not download any .onnx file (download requires permission), so which op types the current deployed model uses is UNVERIFIED.

### E4. Known accuracy caveats
- VERIFIED: open issue microsoft/onnxruntime #29849 "[CPU] MatMulNBits accuracy_level=4 (int8 activation quant) selects wrong argmax token on massive-activation LLMs (Qwen3-0.6B, Phi-3.5-mini)" (opened 2026-07-24, tested on ORT 1.27.0, marked stale 2026-09-11, no fix). On ORT-GenAI's Qwen3-0.6B CPU export (which has 8-bit MatMulNBits nodes) the first greedy token differs between accuracy_level 4 and levels 0-3 (levels 0-3 agree). A contributor's synthetic analysis (M=512,N=2048,K=1024, BlkLen 32): weight-quantization RMS error 4-bit 8.07e-02 / 8-bit 4.75e-03; the int8-activation term is about 5.35e-03 regardless of weight bits, so on 8-bit nodes it is the largest single error term; simulated int16 activations cut it ~256x but roughly halve throughput. This is about generative logits, not embeddings: the effect on Qwen3-Embedding cosine/ranking is UNVERIFIED (nobody has measured it), but the same model family and the same 8-bit nodes make it a real risk. Test: compare embeddings (cosine vs fp32 reference, recall@k on your eval set) with accuracy_level 4 vs fp32/unquantized before shipping.
- Practical consequence (inference from E2): with 8-bit weights on CPU you choose between level 4 (fast, int8 activations, extra error) and any other level (de-quantize fallback: more accurate but slower); no fp32-packed 8-bit kernel exists. A 4-bit/block-32 model could use the new `force_fp32` option instead.

### E5. Prefix / KV-cache reuse for a constant query prefix
- VERIFIED model facts: Qwen3-Embedding is causal-attention, appends EOS, takes last-token (EOS) hidden state; queries are `Instruct: {task}\nQuery:{query}` (HF card) / `{Instruction} {Query}<|endoftext|>` (paper); documents have no instruction. HF recommends `padding_side='left'` and last-token pooling. Transformers.js/ONNX export `onnx-community/Qwen3-Embedding-0.6B-ONNX` is a `Qwen3Model` feature-extraction export with fp32/fp16/q4/q4f16/int8/uint8/bnb4 variants (https://huggingface.co/api/models/onnx-community/Qwen3-Embedding-0.6B-ONNX).
- Reasoning (UNVERIFIED externally, but follows from causal masking): because attention is causal, the KV states of the constant instruction prefix do not depend on the suffix, so reusing the prefix KV is mathematically exact, the same trick as LLM prompt/prefix caching (vLLM documents Automatic Prefix Caching generally: https://github.com/vllm-project/vllm/blob/main/docs/features/automatic_prefix_caching.md; vLLM lists Qwen3-Embedding-0.6B as a supported `embed` model with LAST pooling, https://github.com/vllm-project/vllm/blob/main/docs/models/pooling_models/embed.md). I found NO source documenting this as a standard technique for ONNX-exported embedding models specifically; I also did not confirm whether vLLM enables APC for pooling models.
- Pitfalls to verify before relying on it (UNVERIFIED, reasoned): (1) feature-extraction ONNX exports normally have no `past_key_values` inputs/outputs, so you need a with-past export of the base `Qwen3Model` (I did not download the .onnx to inspect its inputs; unknown for the onnx-community export); (2) `position_ids` must start at prefix_len and `attention_mask` must have length past+new; (3) tokenizer boundary: tokenize prefix and suffix so the concatenation equals the tokens of the full string (note HF snippet uses `Query:{query}` without a space but the TEI example uses `Query: {query}` with a space; pick one and keep the cache key identical); (4) left-padded batches misalign a shared prefix (cache is simplest at batch size 1, which fits online query encoding); (5) cached vs recomputed values differ only by fp rounding, but q8/int8-activation quantization (E4) noise applies either way; (6) gain is small: the instruction is about 20 tokens (estimate), so savings matter mostly for very short queries; Workers AI's `instruction` parameter or DeepInfra's `custom_instruction` avoid the question by doing the prefixing server-side.
