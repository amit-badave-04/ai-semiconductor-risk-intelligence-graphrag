# Council 7: after window W1 - adopt the fp32 embedder on live (0.6% memory margin)? and what to do with S2 now that R1 fails

Run 2026-11-05 (workflow wf_bee3eb37-9db): five Sonnet advisors, five Sonnet peer reviewers (anonymized), Opus chairman.

## Framed question

CONTEXT. Semigraph is a public demo site (FastAPI on ONE Fly.io machine, shared-cpu-2x with 4 GB, in Singapore; the owner pays all costs and requires approval for any new recurring cost; a failed pre-registered gate is never waived by the builder). Every live question is embedded on the server CPU by a Qwen3-Embedding-0.6B ONNX model before retrieval and a cited LLM answer. Uploads (private workspaces, max 30 pages / about 16,000 tokens) are embedded by the same model.

THE CANDIDATE: today's model ("q8") stores 8-bit weights that ONNX Runtime 1.29 dequantizes on EVERY call. A float32 version ("fp32") dequantized once offline keeps retrieval identical (all four pre-registered parity gates pass; on the Linux builder the cosine to q8 is 1.000000000 mean and min over 53 questions; dequantization bit-exact on all 196 nodes).

MEASURED ON FLY TODAY (window W1, one-off machines, Linux, gate evidence):
- Timing (pre-registered gate 2 "candidate median beats today's on shared-cpu-2x and performance-2x over >= 50 interleaved calls"): PASS on both. shared-cpu-2x with a fresh burst balance: q8 1.19 s -> fp32 0.33 s (3.6x). shared-cpu-2x after the burst balance was drained (the live machine's normal state under sustained load): q8 9.96 s -> fp32 2.76 s (3.6x). performance-2x: q8 1.41 s -> fp32 0.44 s (3.2x).
- Throttle (window W0, still running): a NEW shared-cpu-2x ran at full speed for about 116 s, then fell to about 15-18% of that throughput (steal about 46%). The live site's start script creates a new machine each time.
- Memory, one model per process, with 60 query embeds and the M4 max-size upload workload (15,849 tokens of passages): q8 peak 867 MB; fp32 peak 2,127 MB (2.06 GB anonymous: the weights are private memory, not a shared file mapping); delta +1.26 GB. Prediction method (written before the run): live uvicorn peak = M4's measured 1,125,116 kB during a max-size upload + delta = 2,385,128 kB against the 2,400,000 kB uvicorn limit set in M4 -> PASS with a 14,872 kB margin (0.6%). Context: M4's budget on the 4 GB machine was uvicorn <= 2.4 GB plus an upload-parse child process capped by RLIMIT_AS at 1 GiB (its measured peak was 41 MB), total budget 2.8 GB; the machine reports 4,013,312 kB total. An out-of-memory kill would cut every in-flight answer stream and restart the process (paid asks in flight are then charged their estimate at boot: money-safe, but a visible failure).
- S2 feasibility (council 6's pre-registered rule R1: run the paid benchmark / expect S2 to pass only if the predicted S2 embed load on performance-2x is <= 1.1 core-s/s at 2.6 live asks/s with salted questions): fp32 salted median 0.68 s (embed_rss's 30 benchmark questions; the salt adds 22.7%) -> 1.77 core-s/s; or the timing script's 0.44 s x 1.227 -> 1.39 core-s/s. Either way R1 FAILS, and S2's own CPU gate (<= 70% of 2 cores = 1.4 core-s/s for everything, embedding included) is predicted to FAIL on a single performance-2x even with fp32. S2 (1,000 virtual users, mock LLM, about $1.25, cap $2.00) is pre-registered; "a failure stays a failure; a bigger size is a new run". Its outcome was meant to decide whether a shared state store or a bigger live machine is ever needed.
- Prices (Fly, sin, per 30 days): shared-cpu-2x 4 GB $32.24 (live today); RAM is $6.00/GB-month x 1.2692 (sin), so 8 GB on the same class is about +$30/month (derived); performance-2x 4 GB $83.77.

DECISION 1: Should the builder recommend adopting fp32 on the live site, and with what memory safeguard? Options include: adopt as is (0.6% margin); adopt and lower the upload size cap to widen the margin (e.g. fewer pages/tokens; measure); adopt and raise the live machine to 8 GB (new recurring cost, owner approval); adopt with a memory guard (refuse uploads while memory is high); keep q8 (hold).
DECISION 2: What should happen with S2? Options: run it on performance-2x anyway to record the predicted FAIL with its maximum sustained rate; skip it and record "not attempted, predicted to fail by R1 on measured Fly numbers"; pre-register a NEW run on a bigger class (e.g. performance-4x, or two machines) before any spend; or change what M5 claims (e.g. state the measured per-machine live-ask capacity instead of the 1,000-user claim).
Answer both decisions with concrete parameters and the order of actions.
