# Council 5: S2 live-pool realization (owner item P): keeping live asks uncached in the 1,000-user staging test

Run 2026-10-07 (workflow wf_3680c395-34f): five Sonnet advisors, five Sonnet peer reviewers (anonymized), Opus chairman.

## Framed question

CONTEXT. Before promoting a new serving stack for a public demo site (FastAPI on Fly.io, answers questions about SEC filings with LLMs and a Neo4j graph), the team runs a PRE-REGISTERED load test "S2" on a temporary staging copy: one performance-2x 4 GB Fly machine for the API, a clone of the Neo4j database, a mock LLM server that streams OpenAI-compatible answers with realistic timing (no provider spend), and a Locust load generator. Pre-registered and NOT changeable now: 1,000 virtual users, think time uniform 120-300 s, about 2.6 LIVE (paid, uncached) asks/s and about 2.1 CACHED asks/s, about 40 concurrent live answer streams, at least 60 minutes, cold start. Pass: time-to-first-event p95 <= 1.5 s, 40 streams held with 0 drops, errors < 0.5%, CPU <= 70% of the class's sustained CPU, no thread-pool starvation, zero lost ledger rows, zero cap overshoot in a 10-minute sub-run with the cap set below demand. Void rule: S2 is void if the ledger-measured paid asks/s over the soak is below 95% of 2.6. The result will be cited to the owner as "one machine passed (or failed) the 1,000-user test with a mocked LLM"; it decides whether a shared state store or a bigger live machine is needed (recurring cost of about $9-52/month).

THE PROBLEM ("item P"). The live-question pool is about 300 real questions. The site caches answers by normalized question text: after the first pass, every pool question becomes an answer-cache hit (served free: no embedding, no retrieval, no LLM), so the live rate collapses and the run is void. Separately, the server keeps an in-memory LRU of the last 2,000 query embeddings; the query embedding (ONNX Qwen3-0.6B on CPU, about 1-1.2 s of one core per question) is the dominant CPU cost of a live ask, so repeating pool questions would also make embedding nearly free and the CPU gate would pass for the wrong reason. In real traffic a live ask is by definition one whose answer was not cached, so its embedding is almost never in the LRU either. The owner was told this choice "changes how the pre-registered model is realised" and is decided before the run.

OPTIONS:
(a) Staging-only server settings: skip answer-cache writes for pool questions (live pool always misses; a separate small set of example questions is pre-cached to supply the 2.1 cached/s) AND disable the query-embedding LRU. Retrieval and prompts stay byte-identical to the pool questions. Adds two staging-only code paths to the server, guarded by staging boot validators so production cannot enable them (these code paths ship in the production image, switched off).
(b) A per-ask salt: the load generator appends a neutral unique token to each live question (e.g. " (ref 48213)"), which changes the cache key and the embedding input, so both caches miss naturally and server code is unchanged; cache writes still happen as in production. Retrieval is not byte-identical (the salt perturbs the embedding slightly; the mock LLM does not care); the staging cache grows by about 10k rows per hour; the salt must not trip question validation, company/alias detection or length limits; a pre-run check can measure how often the salted question's retrieval differs from the unsalted one.
(c) A much larger generated pool (tens of thousands of paraphrases): realistic diversity but costs effort and LLM money to generate and shifts the retrieval distribution.
(d) Something else.
CONSTRAINTS: pre-registered numbers cannot change; the realization must not make the test easier than real traffic; production code changes are a risk (they ship); staging is torn down after; minimal cost.

QUESTION: Which realization should S2 use, and what safeguards make the result trustworthy?
