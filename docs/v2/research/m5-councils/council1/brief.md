# Council 1 brief: compute and fleet for the M5 "1,000 concurrent users" gate

## The product and the owner's constraints
- Semigraph: a cited GraphRAG over SEC filings (13 filers) and BIS rules. FastAPI + SSE on Fly.io (region `sin`), a Neo4j Community machine (1 GB shared), Cloudflare Turnstile bot gate. Today ONE API machine (`shared-cpu-2x`, 4 GB, ~0.9-1.1 GB RSS), one uvicorn process. Per-IP paid window 5 asks / 10 min; global ceiling 150 paid asks/day.
- It is a DEMO to a potential buyer. Real human load will be a handful of people. "1,000 concurrent users" is a capability claim the owner wants PROVEN by a load test (recorded decision, 2026-09-25: "1,000 concurrent users, provable by a load test"). The load test uses a MOCK LLM, so it proves the app tier, database reads, admission control and the degrade path, not provider capacity.
- Owner rules: demo-grade, standard proven methods, no shortcuts ("we have time, do it the right way"); NEW recurring hosting cost, NEW vendors/accounts need the owner's explicit decision; a failed gate is reported, never relabelled; honest public claims.
- The load model is pre-registered (docs/v2/PLAN.md:33): 1,000 virtual users, think time uniform 120-300 s (mean 210 s => 4.76 iterations/s), each iteration is exactly one ask: 45 % cached example (no LLM, no embedding), 40 % live question from a 300-question pool (query-embedding cache hits expected after the first ask), 10 % live unique, 5 % live agent. Derived: ~2.6 live asks/s and ~2.1 cached asks/s; with a 15 s mean stream ~40 concurrent live streams (~60 in a 1,500-VU spike). Gate (steady + 60 min soak): live-ask time-to-first-event p95 <= 1.5 s, >= 40 concurrent live streams held with 0 drops, errors < 0.5 %, per-machine CPU <= 70 % of that class's sustained CPU.

## Measured this week (local desktop, onnxruntime 1.29.0 = the production pin; threads = 1 unless stated)
1. Query embedding (Qwen3-Embedding-0.6B, 8-bit `MatMulNBits`, ~32 tokens including a constant 17-token instruction prefix): **1.22 s** at 1 thread, 0.91 s at 2, 0.66 s at 4. 98 % of the time is inside `MatMulNBits` (ORT's own per-operator profile: 1.177 s of 1.199 s). There is a fixed floor of ~1.0 s even for a 4-token input (1.05 s). That shape is consistent with every weight being dequantized to float32 on every call (a hypothesis; the profile shows only the time share).
2. The shipped model was built WITHOUT the `accuracy_level` attribute (the builder script calls `DefaultWeightOnlyQuantConfig(block_size=128, is_symmetric=True, bits=8)` and nothing else).
3. Setting `accuracy_level=4` (int8 compute) on the 196 `MatMulNBits` nodes of the SAME weights (attribute only, no re-quantization; tested on a scratch copy): **0.31 s** at 1 thread, 0.18 s at 2, 0.11 s at 4; a 4-token input 0.046 s; 45 tokens 0.42 s. Long passages barely change (257 tokens 2.74 s -> 2.48 s), so document embedding for uploads is unaffected.
4. Retrieval parity, 53 benchmark/example questions against the real 3,152 corpus vectors (brute-force cosine): query-vector cosine to the current model mean 0.9988 (min 0.9983); the top-8 set is identical for 83 % of questions (mean overlap 0.979, min 0.875); top-1 identical for 96 %; the differences are boundary swaps at ranks 8-10; max top-10 score gap 0.0077. For scale: the current 8-bit model versus the fp32 reference was cosine mean 0.9992 / min 0.998 (the builder's own check, 20 questions).
5. NOT measured: the downstream answer benchmark with the patched model (a paid eval run, about $1.5-2); the same timings on Fly hardware; CPU per ask outside embedding (prompt build, SSE writes, Neo4j client, verification), which the baseline spike S2 will measure.
6. Tried and rejected: reusing a precomputed KV cache for the constant instruction prefix. The current ONNX export rejects a non-empty cache (invalid expand shape); it would need a re-export. Not pursued.
7. From the owner's live G4 test last week: document embedding on the Fly `shared-cpu-2x` ran at 71.2 tokens/s versus 87.8 on the desktop (the Fly core is ~19 % slower), and over a 4-minute full-core burn the steal was 0.5 % (burst balance not exhausted).

## Derived (assumes the Fly core is 19 % slower than the desktop; UNVERIFIED on Fly)
- One question embed ~0.37 s of one core after the fix versus ~1.5 s today.
- At 2.6 live asks/s: embedding load = about **1.0 core-s/s if every ask is a cold embed** (3.9 today), and about **0.33 core-s/s warm** (pool questions hit the embedding cache; the plan assumes ~0.9 cold embeds/s warm; 1.3 today).
- A question embed must never run on the event loop; it runs on worker threads, bounded by a per-machine "embedding slots" limiter.

## Options on the table
- A. Ship the embedder fix (accuracy_level=4, in the model builder and the image, gated on parity and a re-run of the answer benchmark). Keep the LIVE fleet at one `shared-cpu-2x`. Prove the 1,000-VU gate on a TEMPORARY staging fleet of performance-class machines, destroyed after each test window; publish the runbook for scaling the live site to the proven fleet; admission caps protect the live machine. Documented plainly: the live fleet is not the proven fleet.
- B. Ship the embedder fix AND run live on the machine class that was proven (for example one `performance-2x` 4 GB at $83.77, +$51.53 over today), so live == proven.
- C. Ship the fix and run two smaller dedicated machines live (for example 2 x `performance-1x` 4 GB = $114.24; or 2 x performance-1x 2 GB = $83.78), for redundancy during deploys as well as capacity.
- D. Do not touch the embedder; add hosted query embedding for the public corpus (a new vendor, per-token billing; uploads stay on local ONNX).
- E. Original plan: no embedder change; prove on a larger temporary fleet (about 3 x performance-2x).

## External facts on the embedder and hosted embedding (VERIFIED 2026-10-03 from vendor docs/GitHub; "UNVERIFIED" where marked)
- ONNX Runtime `MatMulNBits.accuracy_level`: 0 unset, 1 fp32, 2 fp16, 3 bf16, 4 int8. On CPU only level 4 selects the int8 path (activations quantized per block); at any other level 8-bit weights fall back to dequantize-then-float-GEMM, which matches our profile. The 8-bit int8 path first shipped in ORT 1.22.0 (x64); production pins 1.29.0. An open ORT issue (#29849) reports level 4 changing the first generated token on Qwen3-0.6B with 8-bit nodes (a text-generation report; its effect on embeddings is UNVERIFIED by them, and our own parity measurement above is the direct evidence for embeddings).
- Hosted Qwen3-Embedding-0.6B: Cloudflare Workers AI `@cf/qwen/qwen3-embedding-0.6b` at $0.012 per million tokens (a free daily allowance exists; exact prompt template and output dimension UNVERIFIED); DeepInfra at $0.01 per million tokens, OpenAI-compatible route, the caller must add the "Instruct: ... Query:" prefix itself, inputs not stored or used for training (latency and "US host" UNVERIFIED). Together has no serverless embedding models; Fireworks serves only the 8B model serverlessly (a different vector space). No host documents the numeric precision it runs (fp16/fp32), and Qwen's own card shows two slightly different templates ("Query:" vs "Query: "); switching would need a live cosine/overlap check against our local vectors, template, normalization and 1024 dimensions. The owner chose LOCAL embedding earlier ("no remote embedding backend without owner sign-off").
