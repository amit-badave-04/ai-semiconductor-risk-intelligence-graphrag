# Council 2 brief: shared state, Valkey, failure policy and caps for M5a

## What Council 1 already decided (binding inputs; do not re-litigate)
- Ship the embedder fix (question embed 1.22 s -> ~0.31 s on a desktop core) behind parity, benchmark and on-Fly timing gates. Hosted query embedding: rejected.
- The LIVE site stays ONE `shared-cpu-2x` (4 GB) behind its caps. The "1,000 virtual users" gate is proven on a TEMPORARY staging fleet of performance-class machines, sized from baseline spike S2 (one machine if S2 shows one passes), destroyed after each window. The claim is worded as a staging-fleet claim; the load generator runs in `sin`; every gate run starts cold; staging may stub Turnstile and raise caps only in staging config.
- The pre-registered load model (docs/v2/PLAN.md:33): 1,000 virtual users, think time 120-300 s, one ask per iteration (45 % cached, 40 % live from a 300-question pool, 10 % live unique, 5 % live agent) = ~2.6 live asks/s, ~2.1 cached/s, ~40 concurrent live streams.

## The question this council must settle
The M5 plan was written assuming a multi-machine live fleet. With live staying on one machine, is a NEW shared state store (self-hosted Valkey) needed now, later, or never? The plan as written builds it now.

## State today (verified in the code)
- A paid ask (`POST /api/ask`, serve/routes.py) passes these gates in order: validation; a per-IP "free" window; (workspace token check, or the answer-cache read); the kill-switch read; today's paid-ask COUNT read (a count over the day's `SvcQuery` rows) against the 150/day ceiling; Turnstile; the per-IP paid window (5 / 10 min); then the stream. Service-state operations in Neo4j per live ask: 3 reads before streaming (answer cache, kill switch policy, paid-today count) and 2 writes after (the `SvcQuery` ledger row, the cached answer). A cached ask: 1 read + 1 write. At the gate load that is roughly 12 reads/s and 9 writes/s of SERVICE state, besides ~5 retrieval reads per live ask. Neo4j (Community, a 1 GB `shared-cpu-1x` machine) has NOT been measured under that load; the plan's statement that Neo4j cannot carry it is an assumption (spike S7 would measure 5/10/20 asks/s).
- In-process (per machine) state: the per-IP limiters (free 30/10 min, paid 5/10 min, read 120/min, workspace-create 3/day, upload 10/hour), the answer-slots semaphore (today 2 concurrent LLM streams per machine; the async rewrite is what lets a machine hold dozens), the upload slot (1), the upload-job registry and job SSE fan-out (a watcher on another machine cannot see a job), the freshness monitor's cached last result (its lease lives in Neo4j), the boot-fixed snapshot id / example ids / graph stats. Process-local state is CORRECT on one machine and wrong on several.
- The ask stream is a synchronous generator driven through a thread pool (one thread hop per token), the embedding runs on the pool, and Neo4j calls share the same default 40-thread pool. The async rewrite of the answer path (no thread per stream, cancel on disconnect, embedding on bounded worker threads) is required for ANY scale and is not in question here.
- Durable data that must survive: the `SvcQuery` ledger (source of the all-time cost figures), cached answers (the 53 seeded examples never expire), uploads (24 h, private), policy (kill switch).

## What the plan builds (docs/v2/M5_PLAN.md, section 4.1-4.5)
A `serve/state/` package with THREE backends behind one protocol (`valkey` for production, `neo4j` wrapping today's persistence as the rollback, `memory` for tests), four hand-written Lua scripts (reserve / renew / reconcile / sweep: atomic daily count + spend ceiling + fleet in-flight cap with lease TTL), per-IP windows in Valkey via the `limits` library, an answer cache and a 4 KB-per-entry query-embedding cache, job-progress streams for cross-machine SSE, a sweeper lock, drain on shutdown, and a self-hosted Valkey on its own Fly machine with a volume. One worker (of three) owns the whole package plus parity tests across the three backends.

## Verified facts (2026-10-03, vendor docs/GitHub; UNVERIFIED where marked)
- Self-hosted Valkey on Fly in `sin`: shared-cpu-1x 1 GB $8.50 + a 1 GB volume $0.15 = about $8.65 per 30 days. The official `valkey/valkey` image: RDB snapshots on by default, AOF OFF, no VOLUME declared (so you must mount a volume at /data and set `--appendonly yes`). Valkey stable is 9.1.2 (2026-08-31), a security release that fixes an unauthenticated Lua use-after-free: pin 9.1.2 / 9.0.6 / 8.1.10 / 8.0.11 or later. A machine with a volume has downtime on every deploy (Fly doc); a single Valkey has no HA. Fly's private DNS has a reported stuck-resolver bug (2026-09-15): clients must retry DNS.
- Fly-managed Upstash Redis: maintained, no sunset notice; NOT stock Redis or Valkey (Upstash's own compatible engine); pay-as-you-go $0.20 per 100k commands (about $0.72 per hour at ~100 commands/s), a 10,000 commands/s throttle; EVAL/EVALSHA, streams and blocking reads are documented; reachable only over private IPv6; no published latency; whether `sin` is selectable is UNVERIFIED; 2026 incidents on Fly: unstable connections 2026-03-29 and a multi-hour outage 2026-05-11/12.
- Python clients: `limits` 5.8.0 (latest) pins `redis<8` and has an officially supported `valkey://` storage through valkey-py, CI-tested against Valkey 7.2 and 8.0. redis-py 8.x defaults `socket_timeout` to 5 s, which breaks blocking stream reads longer than 5 s unless overridden. Whether our Lua and stream usage runs unchanged on Valkey is documented-compatible but NOT tested by us.
- Org-level billing quirk: same-region app-to-app traffic is free only for Fly orgs on "granular" rates (our org is a personal org of unknown creation date); the worst case for a self-hosted store is the public rate $0.04/GB, a few dollars a month at gate traffic, negligible at demo traffic.
- Owner constraints: new recurring cost and new vendors need the owner's explicit approval; honest reporting; a failed gate is never relabelled; the deploy of one live machine is a rolling restart that drops open streams (kill_timeout max 300 s, best-effort).

## Options
- S1. Build the plan as written now: Valkey (self-hosted) + three backends + Lua, fail-closed.
- S2. Defer Valkey: build the async rewrite and a `StateBackend` protocol with two backends now (in-process = today's behaviour on one machine, `neo4j` = today's persistence); run S2/S7 on staging on ONE performance-class machine; add the Valkey backend and its machine only if S2/S7 show the gate needs more than one API machine, or the owner later wants a multi-machine live fleet. Same interface, so the later Valkey is a drop-in, not a rewrite.
- S3. As S1 but with Fly's Upstash Redis instead of self-hosted Valkey.
- S4. Keep Neo4j as THE shared store and make multi-machine staging work through it (no new store, ever).

## Also to decide (the plan's proposed policy defaults; the owner mostly agrees with the plan)
- Daily spend cap `max_spend_usd_per_day = 10` with atomic reserve/reconcile on an estimate (expired lease is charged its estimate); three-level kill switch (on / retrieval_only / off); per-machine embedding slots (1 per shared machine) and a per-machine in-flight LLM cap; per-IP hashing moves from an unsalted hash to an HMAC with a NEW secret `IP_HASH_PEPPER` and IPv6 bucketed by /64; the Langfuse hash salt becomes a shared secret.
- If a shared store is used and becomes unreachable: fail CLOSED for paid answers (503 with the paused copy; reads, evidence, workspaces unaffected; cached answers unavailable) versus fail OPEN (unmetered).

## What we need from the council
(1) Which of S1-S4 for M5a, and the evidence that would change it; (2) if a shared store is adopted now or later, self-hosted Valkey versus Upstash, the client library, the persistence/eviction settings, and the failure policy with exact per-feature behaviour; (3) accept or amend each proposed policy default; (4) the order in which M5a should be built so that S2 and S7 can run as early as possible; (5) the biggest risk in your chosen path and how to detect it early.
