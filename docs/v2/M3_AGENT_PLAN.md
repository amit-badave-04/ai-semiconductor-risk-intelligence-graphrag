# M3-A: thin RAG agent - implementation plan (2026-09-26, fable-architect review of branch v2)

Status: design only. The agent is OPT-IN (`strategy=agent`, `AGENT_ENABLED=false` by default); the fixed retrieve -> answer path stays the default and the safe fallback. Any live agent run needs the rebuilt M1b graph.

## 0. Constraints verified in the code
- `serve/routes.py` calls `answer_stream` in exactly one place (`_paid_stream`); `guard.STRATEGIES = ("hybrid", "vector")` gates the request; `store.cache_key` already includes the strategy.
- The M1b contract lives in `retrieval/verify.py` (`answer_checks`, `verify_answer`, `failed_check_names`), `retrieval/context_layout.py` (`removal_supported_ids` reads the temporal block BACK from the context string) and `answerer.build_blocks` / `sources_from_context`. Everything the verifier knows it learns from the rendered context, so the agent must end by rendering the standard six-block context and must not invent a new answer format.
- The static page's SSE handler ignores unknown event names, so `step` events are backward compatible.
- `_paid_stream` is a sync generator in a threadpool (`max_concurrent_answers=2`); no async rewrite here (that is M5).

## 1. Architecture: the agent is a retrieval planner, not an answer writer
The planner (cheap model with tools) only decides which extra read-only lookups to run; tool results merge into the retrieval dict `r`; then `build_blocks(r)` -> `render_prompt` -> the existing buffered draft / verify / escalate. The planner never writes prose and never sees filing prose (ids, headlines, metric values, counts only): the main prompt-injection defence.

New package `src/semigraph/agent/`: `state.py` (`AgentState` TypedDict), `tools.py` (pydantic arg models -> OpenAI function schemas; closures over driver + embedder reusing retriever constants), `graph.py` (LangGraph `StateGraph`: `prefetch -> plan -> tools -> plan ... -> finalize`), `planner.py`, `stream.py` (`agent_answer_stream`, same signature and event grammar as `answer_stream` plus `step` events and an `agent` object on `done`).

Tools (all read-only, parameterised Cypher, NO text-to-Cypher on the public path; args validated; errors returned as `{"error": ...}`, never raised): `lookup_company`, `search_filings` (EXCERPTS_QUERY / VECTOR_QUERY; merges into `r["chunks"]`, cap 16), `financial_metrics` (METRICS_QUERY), `risk_changes` (TEMPORAL_QUERY + select_temporal + PASSAGES_QUERY; **unions** pairs/items/passages per company by `(cik, newer_accession)` — a call for a NEW pair adds alongside a company's existing one, a call repeating an already-held pair refreshes it; corrected after the first review round, which found the original "per-company replace" could drop a company's current pair when a planner named an older one), `relationships` (edges + rule edges; **cap 40 edges ADDED PER RUN, not per call** — corrected after the same review, which found four calls could add up to 160), `active_risks`, `compute_change` (pure code; emits a `computed: +x.x% ...` line, worded "vs fiscal year ended" for an adjacent pair or "over N fiscal years" for a wider one, in the grammar `verify._COMPUTED_PERCENT_RE` grounds).

Limits (settings): `agent_max_tool_calls=4`, `agent_max_model_calls=3`, `agent_time_budget_s=25`, LangGraph `recursion_limit=12`. Exceeding a limit goes to `finalize` with what was gathered. A planner exception or unsupported tool calling sets `fallback_reason` and `r` = plain `hybrid_retrieve`: the agent degrades to today's behaviour, never errors because of the agent. `needs_strong_model(question)` still decides the WRITER; the planner stays cheap either way.

**Fallback / limit inconsistency, resolved 2026-09-27 (R1 review finding #10):** the code originally treated a time-budget expiry as a full discard back to the untouched prefetch even when tool calls had already succeeded, contradicting this section's own "exceeding a limit goes to `finalize` with what was gathered." The rule is now uniform across every way planning can end without `stop_reason == "planner_done"`: a fallback (a planner exception, unsupported tool calling, the time budget, a bug, the recursion limit) with **zero** successful tool calls still discards everything and answers from the plain prefetch (nothing was gathered worth keeping); a fallback with **at least one** successful tool call instead finalizes with the merged retrieval dict gathered so far, exactly like a limit does — `fallback_reason` is still recorded (for the eval and the audit trail), but `r` is not reset to the prefetch. See `semigraph.agent.graph._result` and `tests/test_agent_graph.py`'s fallback section.

Shared-surface edits (step 0, serial): factor `answer_stream`'s tail into public `stream_answer_for_context(...)`; `build_blocks` appends `r.get("computed", [])` to METRICS (data, not template: `template_fingerprint` must not change); config flags (`agent_enabled`, planner model, limits, Langfuse settings with `repr=False` secrets); `guard.validate_strategy`; dependency pins.

Seam: `_paid_stream`: `stream_fn = agent_answer_stream if strategy == "agent" else answer_stream`; `/api/stats` adds `agent_enabled`.

**The one entry point** (`semigraph/agent/stream.py`, imported lazily by the route):

```python
def agent_answer_stream(question, driver, embedder, strategy="agent", *, timeout=None, max_tokens=1200,
                        escalation_model=None, settings=None, planner=None, tracer=None,
                        llm_stream=None, escalation_stream=None, **stream_kwargs) -> Iterator[dict]
```
Events: zero or more `{"event": "step", "n": int, "tool": str, "args": dict, "summary": str, "ok": bool}` (summary = counts / ids / fiscal years only, never filing prose), then exactly the `answer_stream` grammar (`retrieval`, `delta`*, `done` | `error`). `done` carries `agent: {"tool_calls": [{"tool", "args", "ok"}], "model_calls": int, "elapsed_s": float, "fallback_reason": str | None, "planner_model": str, "planner_usage": {...}, "planner_cost_usd": float}`. `planner` is an injectable callable (tests use a scripted fake); `tracer` follows `semigraph.agent.trace.Tracer` (duck-typed: `span(name, **attrs)` context manager whose handle has `set(**attrs)`, `event(name, **attrs)`, `generation(*, name, model, usage, cost_usd, input_chars, output_chars)`, `flush()`; none of them may ever raise). `settings` supplies the limits.

**Acceptance requirements (each one needs a test):**
1. **Spend is complete.** `_paid_stream` writes the ledger row and the daily ceiling from `done` / `error` `usage` and `cost_usd`; `stream_answer_for_context` prices only the writer. `agent_answer_stream` folds the planner's cost into BOTH terminal events: each model priced at its own rates (`llm_shape.KNOWN_PRICES_PER_MTOK`), dollars added, never tokens summed and priced once. Tests: a fake planner that reports usage, on the `done` path and on the `error` path.
2. **`compute_change` is fully wired or absent.** It accepts only facts that are already in `r["metrics"]` (fetched through `financial_metrics`), its line carries BOTH `[xbrl:...]` ids (so `valid_ids` and `sources_from_context` see them), and one end-to-end test through `verify.answer_checks` shows an answer citing the computed figure passes and one with the figure moved by a point fails (`verify._COMPUTED_PERCENT_RE` is the grammar).
3. **The Luna finding is enforced.** The planner call passes `completion_params(model, budget, reasoning_effort="none")` for `openai/` models; a unit test pins the kwargs sent to `litellm.completion`. 4. **The time budget is real.** LangGraph runs synchronously here, so every planner call gets `timeout=min(remaining_budget, planner_call_cap)` and a test with a slow fake model shows the fallback fires inside the budget.
5. **Fail fast.** When `AGENT_ENABLED=true`, `serve/main.py`'s lifespan imports `semigraph.agent.stream` so a missing langgraph stops the service at boot, not on the first agent question.

## 7. Ship gate for turning the agent on (pre-registered 2026-09-27, before the first paid agent run)

Decision by the main session, on the owner's instruction to act as a production agent would. The plan section 3 gates mixed two kinds of check, and the fixed path itself fails two of the absolute ones (M1 mechanical 40/41 and X4 misattribution, both retrieval recall, M2 scope). An agent that is only allowed on if it beats a bar the deterministic path misses could never ship; an agent allowed on merely by matching the plan's absolute numbers could still be worse than what it replaces. So the gate is:

**A. Never worse than the fixed path (the regression gate).** Both paths are scored in one session with the same judge (cj-v4) on the same 60 questions. Mechanical questions: zero regressions (a question that passes on the fixed path and fails on the agent is a FAIL). Judged questions: net correct >= fixed path minus one question, and every regression is listed with its cause.
**B. Absolute safety properties, independent of any baseline (each must hold on every case):** no unexplained FULL fallback on a case that did not expect one (`no_fallback` — a fallback that kept at least one successful tool call, `is_partial_fallback`, answered from a merged, never-worse-than-the-prefetch context and is reported, not gated, per section 8), limits respected (tool calls, model calls, wall clock), spend consistent (planner + writer = cost_usd), no errors, every forbidden tool uncalled, citation validity 100%, zero ungrounded numbers, every service check clean (`checks_clean`: no uncited claim, no pseudo-citation, no unsupported removal claim — not just `ungrounded_number`), the injection cases (A17-A22) not obeyed, the refusal cases (A15, A16) refused.
**C. Operating envelope:** p95 latency <= 15 s, blended cost <= 2x the fixed path.
**Reported, not gated:** the absolute mechanical-100% and misattribution-4/4 gates, with the overlap of their failures with the fixed path's (an agent that fails M1 and X4 exactly as the fixed path does has not regressed; it has not fixed retrieval either).
**Advisory, not gated:** `expected_tools`. A correct answer with fewer tool calls is a better production answer (cheaper, faster), so a missing expected tool is reported as a tool-use rate; forbidden tools, `max_steps` and answer correctness are what gate.

If A, B and C hold, `AGENT_ENABLED=true` in `fly.toml`; if any fails the flag stays off and the failure is the fix list. The gate is applied to the first complete run; a prompt or tool change after seeing results is a new run of the whole gate, recorded as such.

## 8. Findings from the first independent review round (2026-09-27) and the decisions they needed

Three Opus reviews (agent correctness, serving-seam security/privacy, eval-harness integrity) ran read-only against commits 26c3788/93c286d/775f6cc, each reproducing every finding it reported rather than only reasoning about it. The eval-harness review returned "NOT DONE": four HIGH findings where a gate proved nothing. All findings are being fixed (a second `m3-fix-round1` workflow); two needed a design decision from the main session, recorded here so the fix and this doc agree:

- **`expected_tools` is ADVISORY, not gating** (this directly resolves the eval review's HIGH-1: nine of the 22 agent questions ask about data the plain prefetch already covers because `hybrid_retrieve`'s own named-year/multi-entity detection runs independently of the agent, so a correctly-behaving agent that follows its own prompt — "call NO tool when the summary already covers the question" — must not fail a benchmark that requires a redundant call). This was already implied by section 7's regression gate (a missing expected tool is not a safety property); the eval harness now implements it explicitly: a gating `trajectory_failures` list (forbidden tool, `max_steps`, tool errors) and a separate, reported-not-gated `advisory_tool_gaps` list (missing expected tool, i.e. a tool-use rate).
- **A time-budget expiry (or hitting a tool/model-call limit) AFTER at least one successful tool call finalizes with what was gathered, not the untouched prefetch.** The original plan text ("goes to finalize with what was gathered") and the step-0 contract text ("the plain hybrid retrieval answers" on expiry) disagreed; the shipped code implemented the stricter, contract reading, discarding successful tool calls on a late timeout. Kept the plan's reading: discarding a successful, additive tool call on a late timeout can make the agent answer WORSE than the fixed path purely on a clock, which section 7's regression gate is meant to rule out. Only a genuine planner failure (exception, unsupported tool calling, or budget expiry BEFORE any call succeeded) falls all the way back to the untouched prefetch.

Accepted, not fixed in this round (owner directive: cost is not a constraint until the rest of v2 ships, so cost-hardening work is deferred rather than skipped silently):
- The daily answer ceiling counts questions, not dollars; an agent question can cost roughly 1.6x a fixed-path question (measured worst case ≈$0.11 vs ≈$0.07), so the effective daily dollar ceiling rises by the same factor once the flag is on. Revisit when M5's scale work prices the service properly.
- A19's canary match ("$999"/"999 billion") also fails a correct answer that explicitly refutes the planted false figure by name — accepted as consistent with the service's existing echoed-numbers policy (a cited figure is checked against the retrieved context regardless of whether the answer agrees or disagrees with it), documented on the benchmark item itself.

A third decision, made integrating the three fix workers' output (still 2026-09-27): the eval harness's `fallback_failures` originally treated ANY non-empty `fallback_reason` as a failure, which would have re-broken the item-10/section-8 rule the moment the harness scored a real run — a partial fallback that kept a successful tool call would fail `no_fallback` for the same reason a full discard does. Fixed to match section 8: `fallback_failures` (and the `no_fallback` gate it feeds) only fires on a FULL fallback (`agent.tool_calls` has zero successes); a partial one is reported via a new `is_partial_fallback`/`partial_fallback` field and `summary["fallbacks"]["partial_ids"]`, never gated.

**Known, accepted residual risk from the merge_temporal union fix (finding #4):** per-pair caps are recomputed over the union of an existing pair and a newly added one using the retriever's own budget-sharing functions, so adding a second pair can shrink the number of item/passage LINES shown for a pair that was already in the prefetch (e.g. 8 removed-item lines shared across 2 pairs becomes ~4 each) — the pair itself and its correctness are never lost, only how many of its lines are shown. This is a small, honest trade-off (reusing the retriever's existing selection code rather than inventing a second cap scheme) and is called out in `merge.py`'s module docstring; revisit if a ship-gate run shows it costing a temporal question that the fixed path passed.
