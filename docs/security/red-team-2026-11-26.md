## Findings

### M2RT-01 · Low · Confirmed · A held embedding job resumes after a restart without being charged to the daily cap
- **CWE-770 / OWASP API4 (Unrestricted Resource Consumption)**
- **Location:** `src/semigraph/uploads/embed_queue.py` (`submit`: a held task skips `_refusal`; `resume_pending` submits every pending version with `resumed=True`); `src/semigraph/uploads/repo.py` (`RESUMABLE_EMBEDS_SELECT_QUERY` filters only on `embed_state='pending' AND is_current`)
- **Attack path:** a second upload while the workspace (or client) already has an embedding job running is held in memory, uncharged. A restart (deploy, OOM, crash) drops the in-memory hold; `resume_pending` finds the version's pending chunks and resubmits it as `resumed`, which skips the day-cap check. Each restart grants as many free embedding jobs as were held, even when the 23-a-day cap (OD11) is full. The attacker sets up the held state with ordinary use; the restart is not theirs to trigger.
- **Impact:** extra CPU past the daily embedding cap; each job is still bounded by the 3,600 s ceiling and the 48,000-token workspace budget. No data exposure, no cross-tenant effect.
- **Fix:** record on the `UserVersion` that the day was charged (for example `embed_charged_day`) when `_refusal` reserves it, return the marker from the resume query, and resume with `resumed=True` only charged versions; send the others through `_refusal` or mark them keyword-only. Clearing the hold in `stop()` alone is not enough (a crash never runs it).
- **PoC test:** `tests/security/test_redteam_M2RT-01.py` (fails today: 2 versions embedded, the day charged once).
- **Spec reference:** OD11 / R16 (at most N embedding jobs a day).

### M2RT-V01 · Low · Confirmed · Variant of M2RT-01: a held task refused by the cap is embedded after a restart if the keyword-only write failed
- **CWE-770**
- **Location:** `embed_queue.py` `_admit_held` (its broad `except` swallows a non-`WorkspaceGone` error from `_degrade` -> `repo.finish_embedding`), then `resume_pending`.
- **Attack path:** the held task is admitted and refused (`daily_limit`, including the fail-closed case when the day counter is down); writing its chunks as keyword-only fails with a database error; the log says "stay keyword-only" but the chunks are still `pending`; the next restart embeds them past the cap. Needs a database fault and a restart, neither attacker-controlled.
- **Fix:** the same marker as M2RT-01 (resume fails closed for uncharged versions).
- **PoC test:** `tests/security/test_redteam_M2RT-V01.py` (2 cases: day full, counter down; both fail today).

### M2RT-V02 · Low · Confirmed · Variant of M2RT-01: a fresh task refused by the cap is embedded after a restart if the keyword-only write failed
- **CWE-770**
- **Location:** `embed_queue.py` `submit` refusal branch -> `_degrade`; `src/semigraph/uploads/jobs.py` `_hand_off_to_embedding` (its `except Exception` emits `embed_error` but never retries the write).
- **Attack path:** as M2RT-V01, on the direct submit path. A database blip that makes the day counter fail closed is likely to fail the following write too, which quietly undoes the fail-closed design after a restart.
- **Fix:** the same marker as M2RT-01.
- **PoC test:** `tests/security/test_redteam_M2RT-V02.py` (fails today).

### M2RT-08 · Low · Confirmed · Concurrent upload bodies are fully buffered before any slot or memory check (spec S2 not implemented)
- **CWE-770 / OWASP API4**
- **Location:** `src/semigraph/serve/workspace_routes.py` (`_read_multipart` / `_read_and_gate_body`: `body += chunk`, `bytes(body)` copy, python-multipart kept in memory because `MAX_MEMORY_FILE_SIZE` equals the cap, `file_object.read()`; the upload slot and `memguard.check_upload` run only afterwards in `_finalize_upload`).
- **Attack path:** a client with a workspace token and a Turnstile pass per upload sends up to 10 uploads at once (the per-IP hourly window); every body is read and parsed in memory together (about 4 x the 15 MiB cap each, about 60 MiB), and all but one then get 429. With one token shared across many IPs the only ceiling is Fly's `hard_limit` of 40 concurrent requests (about 2.4 GB transient on the 4 GB machine, which also holds the embedder, and with M2 the keyword index and reranker).
- **Impact:** availability only (memory pressure, a possible OOM restart, which in turn triggers M2RT-01). M2 did not create this; it slightly reduces headroom. The spec's S2 requirement and its named test `test_concurrent_large_uploads_bounded` were never built.
- **Fix:** a process-wide semaphore or byte budget for upload bodies (sized with the ~4x parse overhead), taken right after the Content-Length check and before the body is read, refusing at once with 429/503 when exhausted; optionally run `memguard.check_upload` before reading; cut the copies (stream into the parser, or spool to a temporary file below the cap).
- **PoC test:** `tests/security/test_redteam_M2RT-08.py::test_concurrent_large_uploads_bounded` (fails today).
- **Spec reference:** `docs/specs/m2-search.md` S2.

## Spec compliance (`--spec`)

Every security requirement of `docs/specs/m2-search.md` section 5 was checked against the code. One is violated: **S2** (concurrent upload memory bound and its test; see M2RT-08). The rest hold, notably: the keyword context field is indexed only and never rendered; upload keyword search is scoped per workspace (cache keyed by workspace id, rows bound to `$ws`, workspace answers never cached); the upload routes are protected by the required `X-Workspace-Token` header; the new Cypher legs take every value as a parameter; the period window clamps its dates.

## Rejected false positives (do not re-raise)

- M2RT-02 / M2RT-06: the global 23-a-day embedding cap can be used up by a few visitors: the owner-approved design (OD11, R16), no worse than the 40-a-day upload cap before it.
- M2RT-03: production validators no longer bound the upload token/chunk caps and the embed-jobs setting: operator-set values only (accepted risk L3).
- M2RT-04: a reranker or keyword-index failure at boot degrades silently and stays degraded until restart: no attacker trigger; an operability item (the RUNBOOK boot-log gate covers it).
- M2RT-05: `_scipy_not_imported` edits `sys.modules` while bm25s imports: with the flags on the first call is synchronous at boot, before any traffic.
- M2RT-07: injection in a keyword-leg SEC excerpt: no attacker writes SEC excerpt text (RT-003 class, fixed in deploy C).
- M2RT-V03: a stopped job whose degrade write failed resumes with fresh limits after a restart: needs a database fault and a restart, no attacker input; bounded by the per-run limits.
